# 5주차 상태 설계 의사결정 기록

> 대상: 홈/상품 목록 상태 전체 (서버·URL·클라이언트·로컬)
> 배경: 도구를 먼저 고르지 않고, 각 상태의 원본(SSOT)이 어디 있는지부터 판별한다.

## 판별 기준

원본 위치 판별 질문을 순서대로 적용한다. 앞선 질문에서 걸리면 뒤 질문은 묻지 않는다.

1. **파생 가능한가?** — 다른 상태에서 계산할 수 있는가 → 예: 상태로 저장하지 않음 (렌더 중 계산 / selector)
2. **서버**: 서버가 관리하는 저장소에 저장되는가?
3. **URL**: 이 상태가 담긴 화면을 링크로 공유하거나 새로고침했을 때 복원되어야 하는가?
4. **Zustand(전역 클라이언트)**: 여러 컴포넌트·페이지가 함께 소비하는가?
5. **useState(로컬)**: 위 어디에도 해당하지 않는 나머지

Zustand vs useState를 가르는 축은 "원본 위치"가 아니라 "공유 범위"다. 영속화(persist) 여부는 별개 속성이며 이번 Basic 범위에서는 고려하지 않는다(새로고침 후 초기화 허용).

## 1. 홈·상품 목록 데이터

### 고민지점

- 소유자는 서버로 명확하다. 쟁점은 캐시 정책(staleTime/gcTime)과 홈·목록 간 공유 범위다.
- 두 응답 모두 `categories`를 포함한다. 이를 공유할지, 각자 받을지 결정이 필요하다.

### 의사결정과정

| 선택지                                   | 장점                               | 단점/리스크                                                       |
| ---------------------------------------- | ---------------------------------- | ----------------------------------------------------------------- |
| categories를 홈·목록 간 공유             | 요청 1회 절감                      | 목록 페이지 진입 시 무조건 홈 API 선행 호출 필요 → 초기 로드 지연 |
| categories를 각 페이지가 독립적으로 요청 | 페이지별 독립 로드, 빠른 초기 화면 | 두 응답의 categories 스냅샷 시점이 다를 수 있음                   |

- `/api/products` 응답에도 `categories` 필드가 이미 포함되어 있어 각자 받는 구조가 API 계약과 자연스럽게 맞는다.
- staleTime 비교: 상품 가격·순위는 실무 경험상 자주 바뀌지 않음. 다만 "구매 직전" 맥락(상세 페이지)과 "탐색" 맥락(홈)의 실시간성 요구 수준이 다르다고 판단.

### 결정

- **소유자**: 서버. TanStack Query 캐시는 원본이 아니라 스냅샷 보관소.
- **공유 범위**: 각 페이지 내에서만 (같은 query key를 다른 페이지가 구독하지 않음 → categories도 페이지별 독립 요청).
- **staleTime**: 홈·목록 모두 오버라이드 없이 **전역 default(20s) 상속**. 서로 비교해 정하지 않고 각자 자기 특성으로 독립 결정 — 목록은 SSR 프리페치(`prefetchQuery`+`HydrationBoundary`) 사용과 잦은 트래픽이 근거, 홈은 오버라이드할 근거가 아직 없어 보류.
- **gcTime**: 둘 다 기본값 5분 유지(명시 설정 안 함).
- **정합성 관련 한계**: staleTime은 신선도를 결정할 뿐, 담기/주문 시점의 가격·재고 정합성 보장이 아님을 인지할 것
- **근거**: 원본이 서버 하나이므로 각자 요청해도 SSOT 위반이 아니다. 스냅샷 시점 차이는 감수 가능한 트레이드오프로 판단.

### 범위 밖 (YAGNI)

- 카테고리 전용 API 분리 — 지금은 각 응답에 포함된 categories로 충분. 카테고리가 여러 화면에서 독립적으로 자주 갱신돼야 할 필요가 생기면 분리 검토.

### 미해결 / 보류

- [x] 홈·목록 staleTime 구체 숫자와 근거 — 해소 (전역 20s 상속, 서로 비교하지 않음)
- [x] gcTime 판단 기준 — 해소 (기본값 5분 유지)
- [ ] "공유 범위 = 각 페이지" 문구가 "이 query key를 구독하는 컴포넌트 집합"을 의미함을 표에 명확히 남길지

## 2. 검색·카테고리·정렬·페이지

### 고민지점

- 소유자는 URL로 명확. 쟁점은 수명과 공유 범위를 정확히 서술하는 것이었다.

### 의사결정과정

- 초안: 수명 "한 페이지의 생명주기와 동일", 공유 범위 "X"
- 반박 1: 공유 범위 "X"는 선택 이유("공유 가능한 데이터")와 모순. 실제 소비자는 목록 페이지 내 여러 컴포넌트(검색 폼·카테고리 탭·정렬·페이지네이션·쿼리의 query key/API 파라미터)와 **URL을 받은 외부 사용자**로, 오히려 가장 넓다.
- 반박 2: "페이지 생명주기와 동일"이면 useState와 구분되지 않는다. URL 상태는 컴포넌트가 죽어도(새로고침·뒤로 가기·링크 공유) 살아남는 것이 존재 이유.

### 결정

- **소유자**: URL (nuqs `useQueryStates`)
- **수명**: URL(히스토리 엔트리)이 살아있는 동안 — 새로고침에도 유지, 링크 공유로 부활, `history: "push"`로 히스토리에 쌓여 앞뒤 이동 시 복원
- **공유 범위**: 목록 페이지 내 컴포넌트들 + URL로 접근 가능한 외부 사용자
- **근거**: 공유 가능하고 새로고침 후 복원되어야 하는 조건 → 판별 질문 3(URL)에 해당. 컴포넌트 상태에만 두면 복원 불가능한 설계가 된다.

## 3. 장바구니·위시리스트 상품

> 비로그인 사용자의 로컬 익명 상태. 서버 쓰기 API가 없어 원본이 클라이언트에 있다.

### 고민지점

- 서버 소유가 유효한 선택지인가? → `GET /api/home`·`GET /api/products` 조회 API만 존재, 장바구니를 저장할 endpoint(POST/DELETE)가 없다. 저장할 곳이 없으므로 서버 소유는 지금 불가능.
- store에 무엇을 저장할 것인가 (데이터 형태) — `Product` 전체 복사 금지 제약과 도메인 정의를 어떻게 반영할지.

### 도메인 배경 (국내 커머스 조사)

- 장바구니 = 구매 의사 확정 상품의 주문 대기 목록. 실무에선 상품 ID + 옵션(사이즈) + 수량을 라인 아이템으로 관리.
- 위시리스트(찜/좋아요/관심상품) = 구매 의사 불확실한 북마크. 상품 ID만, 상품 단위 토글.
- 비회원 상태는 브라우저 저장소(localStorage 등)에, 로그인 시 서버 장바구니로 병합하는 패턴이 표준.
- **이번 과제는 수량·옵션·합계를 범위에서 제외** → 장바구니조차 위시리스트와 같은 "상품 ID 집합 토글" 구조로 축소된다.

### 의사결정과정

| 결정 대상        | 선택지                                             | 결정                                                            |
| ---------------- | -------------------------------------------------- | --------------------------------------------------------------- |
| 소유자           | 서버 / 클라이언트                                  | **클라이언트(Zustand)** — 서버 쓰기 API 부재로 유일하게 성립    |
| 저장 데이터 형태 | (a) `Product` 배열 / (b) 부분 객체 배열 / (c) ID만 | **(c) `Set<string>`** — 상태 판별(포함 여부·개수)에 필요한 최소 |
| 장바구니 수량    | 지금 `Map<id, Map<option, qty>>` / 나중에          | **지금은 뺀다 (YAGNI)** — Basic은 담기·빼기·개수뿐              |

### 결정

- **소유자**: 클라이언트 → Zustand store. TanStack Query 서버 상태와 완전히 분리.
- **저장 형태**: 장바구니·위시리스트 각각 `Set<string>` (상품 ID 집합). 중복 자동 방지, 토글·포함 여부 판정 O(1).
  - ID 타입은 `Product.id`(`src/types/commerce.ts:21`, `string`)에 맞춘다. fixture의 `1340400`은 화면 표시용 번호일 뿐 타입 계약은 문자열.
  - 관심 목록(어떤 상품을 담았나)은 client가, 상품 정보(이름·가격·이미지)는 server가 소유 → 관리 주체 완전 분리. client에는 바뀌지 않는 정보(ID)만 저장.
  - 상세 정보가 필요하면 그때 전용 API로 조회. store에 서버 응답을 복사하지 않는다.
- **수명**: 브라우저 탭의 JS 런타임이 살아있는 동안 — 클라이언트 페이지 이동엔 생존, 새로고침 시 소멸(Basic 허용), 새 탭과 공유 안 됨.
- **공유 범위**: 페이지 전역. 담기·빼기는 상품이 있는 모든 페이지에서 가능한 액션이고, 개수는 모든 페이지 헤더에 표시된다.
- **로그인·서버 동기화 시**: 소유권이 서버로 이관된다. 서버가 원본이 되어 개인화 추천 리소스, 사용자 간/기기 간 공유에 쓰인다. 이때 익명 store를 계정 데이터에 병합할지·버릴지·충돌 처리 방식을 정하고, Zustand 역할을 서버 상태의 임시 입력 또는 UI 상태로 재제한해야 한다.

### 범위 밖 (YAGNI)

- 장바구니 수량·옵션·합계 금액, 장바구니 상세 페이지 — 과제 범위 밖. 실무 확장 시 `Set<string>`을 라인 아이템 배열(`{ id, option, quantity }[]`)로 승격.
- persist(localStorage 영속화) — Advanced A. 수명을 새로고침 너머로 연장하는 별개 축.
- 서버 장바구니 API·로그인 병합 — 로그인 기능 도입 시.

## 4. 헤더에 표시하는 개수

### 결정

- **소유자**: 없음 (파생값). 원본은 항목 3의 `cart`/`wishlist` Set이고, 개수는 그 `.size`. 별도 상태로 저장하지 않는다.
- **수명**: 원본(cart/wishlist)에 종속.
- **공유 범위**: 개수 자체는 헤더만 소비. (원본 Set의 공유 범위가 전역인 것과 구분)
- **선택 이유**: 다른 상태에서 계산 가능한 파생값 → 판별 0번(파생)에서 걸러짐. 저장하면 원본과 개수 두 곳을 동기화해야 하는 중복 SSOT 문제 발생.

### 구독 경계

- selector가 **개수(`s => s.cart.size`)를 반환**한다. Set 참조를 반환(`s => s.cart`)하면 담기·빼기와 무관하게 Set 참조가 바뀔 때마다 헤더가 리렌더되지만, 개수를 반환하면 숫자가 그대로일 때 리렌더되지 않는다.
- **왜 store에 저장한 파생값이 아닌가**: 이 selector는 원본 상태로부터 계산한 값을 반환할 뿐 신규 상태를 정의하지 않는다. `cart.size`라는 필드를 store에 만드는 것이 아니라, 리렌더 최적화를 위해 계산 결과만 구독하는 것이다.

## 5. 제출 전 검색어·일시적 UI 상태

> 항목 2(확정된 검색어=URL)의 짝. 발제 자료(round5)는 "타이핑 중인 글자는 로컬, 확정한 순간의 값만 URL로 승격 — 확정 전과 후는 서로 다른 두 상태"로 명시한다. 이 항목은 그 "확정 전" 절반이다.

### 고민지점

- 모델 선택: debounce 자동 반영 vs 명시적 제출. → 발제 권장이 명시적 확정 모델(round5)이라 **제출 시에만 URL push**로 확정, debounce는 도입 안 함. 따라서 타이핑 중 값은 렌더가 아니라 제출 순간에만 소비된다.
- 그렇다면 타이핑 중 입력값을 어떻게 들 것인가 — React state(controlled)인가, DOM(uncontrolled)인가.

### 의사결정과정 (controlled vs uncontrolled)

판별 기준: **타이핑 중 값이 매 글자 렌더에 쓰이는가.** CLAUDE.md "렌더에 쓰이는 값만 state" 규칙의 직접 적용.

|                   | Uncontrolled (DOM이 원본)                              | Controlled (useState가 원본)                                          |
| ----------------- | ------------------------------------------------------ | --------------------------------------------------------------------- |
| 저장 위치         | DOM 입력 엘리먼트. 제출 시 `ref`/`FormData`로 1회 읽음 | React state. `value`/`onChange`로 매 글자 바인딩                      |
| 필요 상태         | 없음 — useState 불필요                                 | `useState` 1개                                                        |
| 매 글자 리렌더    | 없음                                                   | 있음                                                                  |
| URL→입력창 초기화 | `defaultValue={urlSearch}`                             | 초기값 `useState(urlSearch)`                                          |
| 언제 필요         | 확정 전 값이 렌더에 안 쓰일 때                         | 지우기 버튼 노출·글자수·즉시 검증 등 타이핑 중 값을 렌더에 써야 할 때 |

- Uncontrolled는 타이핑 중 값이 렌더에 안 쓰일 때 성립한다. 그러나 아래 세 요구가 이 전제를 깬다.

### controlled로 가는 이유

- **뒤로가기 동기화**: 뒤로/앞으로로 URL 검색어(원본)가 바뀌면, 입력창도 그 최신 값으로 **강제 갱신**한다(입력 중이던 값 폐기). URL이 SSOT이고 입력창은 그 반영이다. Uncontrolled + `defaultValue`는 remount가 없으면 URL 변경을 따라가지 못한다 → 요구 불충족.
- **검색어 삭제(지우기 버튼)**: 버튼이 입력값 유무에 따라 노출/숨김되거나 클릭 시 입력값을 프로그래밍적으로 비워야 한다. DOM이 원본(uncontrolled)이면 버튼 노출 조건을 렌더에서 판단할 수 없고, 비우는 동작도 `ref.current.value = ''`로 DOM을 직접 조작해야 해 React 데이터 흐름을 벗어난다.
- **키워드 하이라이팅**: 타이핑 중인 값 자체를 검색 결과 목록(자동완성 등)에 렌더로 반영해야 한다. 값이 렌더 입력이 되는 순간 정의상 controlled가 요구된다.
- 위 세 요구 모두 타이핑 중 값이 렌더에 쓰이는 사례라, 판별 기준(143행)에 따라 **controlled**로 확정한다.

**주의 — 금지 패턴**: controlled state를 URL 변경에 맞춰 `useEffect`로 밀어넣는 방식은 발제 round1·CLAUDE.md가 막는 "effect로 파생값을 state에 복사"에 해당한다. 대신 React 공식 권장대로 **`key`로 리셋**한다: 커밋된 URL 검색어를 입력 컴포넌트의 `key`로 주면, URL이 바뀔 때 컴포넌트가 remount되어 최신 값으로 초기화된다(effect 없음).

### 결정

- **소유자**: 확정 전 입력값의 표시 상태는 검색 폼 컴포넌트(`useState`)가 들지만, **원본(SSOT)은 URL**이다. 입력창은 URL 값을 초기치로 받아 편집하는 임시 버퍼일 뿐, 최종 진실은 URL.
- **구현 형태**: **Controlled** (`value`/`onChange` + `useState`). 타이핑 중 값을 렌더에 반영하고, 제출 시 URL로 승격.
- **뒤로가기 동기화**: 커밋된 URL 검색어를 입력 컴포넌트의 `key`로 사용 → URL 변경 시 remount로 강제 초기화. `useEffect` 동기화 금지.
- **초기값**: 마운트 시 URL 검색어를 `useState` 초기값으로(없으면 빈값).
- **일시적 UI 상태**(모달 열림, 드롭다운 열림 등 서버와 무관한 순수 UI): 렌더에 쓰이므로 `useState`. 정의한 컴포넌트 안에서만 소비.
- **수명**: 상태를 정의한 컴포넌트 생명주기와 동일. 언마운트 시 소멸.
- **공유 범위**: 정의한 컴포넌트와 props로 내려준 자식 서브트리로 한정(형제·페이지 전역 아님).
- **근거**: 확정 전 값 자체는 공유·복원 대상이 아니지만, "뒤로가기 시 URL을 따라간다"는 요구 때문에 URL이 원본이 되고 입력 state는 그 반영이 된다. controlled로 렌더에 반영하되, URL→입력 동기화는 `key` 리셋으로 처리해 effect 안티패턴을 피한다.

### 범위 밖 (YAGNI)

- **debounce** — 자동 반영 UX로 바꿀 때. 현재 명시적 제출 모델에선 불필요.
- **입력값 파생 UI**(글자수·즉시 검증 등) — 필요 시 같은 controlled state에서 렌더 중 계산.

## 6. 로딩·에러·빈 결과

> 새 상태를 소유하는 문제가 아니다. 항목 1 서버 상태의 세 가지 표현(pending·error·empty)을 **어디서 어떻게 처리하나**의 문제다.

### 고민지점

- 초안은 "로딩/에러를 컴포넌트가 `useState`로 소유"로 전제했으나, 항목 1(서버가 소유)·CLAUDE.md("로딩은 Suspense, 에러는 ErrorBoundary")와 충돌한다.
- 세 표현은 정체·처리 주체가 서로 달라 한 줄로 묶으면 안 된다.

### 세 표현의 분리

| 표현    | 정체                          | 처리 주체                          |
| ------- | ----------------------------- | ---------------------------------- |
| 로딩    | query 파생(`isPending`)       | `useSuspenseQuery` + Suspense 경계 |
| 에러    | query 파생(`isError`) → throw | ErrorBoundary                      |
| 빈 결과 | data 파생(`length === 0`)     | 컴포넌트 렌더 중 분기              |

- 로딩·에러는 판별 0번(파생)에서 걸러진다 — 컴포넌트가 `useState`로 따로 들면 서버 상태와 중복 SSOT.
- 빈 결과는 _성공적으로 받았는데 배열이 빈_ 상태라 Suspense/ErrorBoundary 대상이 아니다. 데이터 도착 후 렌더 중 분기.

### 결정

- **소유자**: 없음 (서버 상태의 파생). 별도 상태로 저장하지 않는다.
- **경계 배치**: 홈·목록을 **섹션별로 Suspense·ErrorBoundary 분리** → 부분 로딩·에러 표시. 홈이 로딩 중이어도 목록은 성공 표시가 가능하고, 한쪽 에러가 다른 쪽을 죽이지 않는다. 항목 1에서 "홈 query와 목록 query는 독립"으로 정한 것과 정합.
- **상위 광역 경계**: 섹션 경계 위에 더 범용적인 경계 하나를 둔다 — 섹션 경계가 못 잡는 예외(라우트 레벨 렌더 오류 등)의 최종 방어선.
- **빈 결과**: 각 목록 컴포넌트가 `data.length === 0`을 렌더 중 판단해 빈 상태 UI를 보여준다.
- **수명**: 로딩·에러는 query 생명주기에 종속, 빈 결과는 data에 종속.
- **공유 범위**: 각 표현은 해당 섹션 경계 안에서만. "에러가 위로 전파"되는 것은 상태 공유가 아니라 ErrorBoundary 버블링(throw가 가장 가까운 상위 경계로 전달)이다.

### 범위 밖 (YAGNI)

- **재시도(refetch) UI** — Basic 범위 밖. 에러 fallback은 메시지만 표시한다. 확장 시 `QueryErrorResetBoundary` + `resetErrorBoundary`로 "다시 시도" 배선을 추가.
- **빈 상태 CTA·일러스트** — 문구 이상의 유도 UI는 구현 디테일로 미룬다.
