# 5주차 상태 설계 의사결정 기록 — URL 상태 설계

> 대상: 상품 목록 조건(검색·카테고리·정렬·페이지)의 URL 상태 parser 설계
> 배경: [state-design.md](./state-design.md) 2번 항목("검색·카테고리·정렬·페이지")에서 URL을 원본으로 정한 뒤, parser 단위의 세부 결정을 별도 문서로 분리.
> 연관: [server-state-design.md](./server-state-design.md) — query key 정규화와 경계를 공유한다. 6번 항목에서 해당 문서의 결정 하나를 개정한다.
> 표기: 이 문서는 설계 논의를 AI로 정리한 초안이며, 결정 내용과 근거는 직접 검토했다.

---

## 1. 필드별 parser 선택

- 결정

  | 필드       | parser                                   | 값의 도메인                  |
  | ---------- | ---------------------------------------- | ---------------------------- |
  | `q`        | `parseAsString`                          | 자유 텍스트 — 후보 집합 없음 |
  | `category` | `parseAsStringLiteral(CATEGORY_OPTIONS)` | 유한 집합                    |
  | `sort`     | `parseAsStringLiteral(SORT_OPTIONS)`     | 유한 집합                    |
  | `page`     | `parseAsInteger` + 하한 전처리           | 1 이상 정수                  |

- 근거
  - parser 선택은 곧 유효성 검증이다. "URL에 실릴 값의 실제 도메인"을 그대로 타입으로 옮기면, 별도 검증 코드 없이 도구가 잘못된 입력을 막는다.
  - `category`·`sort`는 `parseAsStringLiteral`이 허용값 외 입력을 `withDefault` 값으로 되돌린다. 값 목록을 `as const satisfies`로 선언해 `src/types/commerce.ts`의 `CategoryId`·`ProductSort`와 컴파일 타임에 동기화되므로, 타입과 런타임 허용값이 어긋날 수 없다.
  - `page`는 정수 도메인이라 `parseAsFloat`이 아닌 `parseAsInteger`를 쓴다. 다만 `parseAsInteger`는 정수 여부만 보고 범위는 모르므로 별도 처리가 필요하다(6번 항목).
  - `parseAsStringEnum`은 채택하지 않는다. 원본 타입이 TypeScript `enum`이 아니라 리터럴 유니온이므로 대응하는 enum 객체 자체가 없다.

## 2. 기본값 선언과 매직값 제거

- 결정: 기본값은 parser의 `withDefault`로 선언하고, 값은 리터럴이 아니라 상수 모듈에서 가져온다.
  - `category` → `'all'`
  - `sort` → `'latest'`
  - `page` → `FIRST_PAGE`

- 근거
  - "검색·카테고리·정렬이 바뀌면 페이지를 1로 되돌린다"는 규칙 때문에 `1`이 parser 기본값과 세터 세 곳(`setQuery`·`setCategory`·`setSort`)에 총 네 번 등장한다. 같은 의미의 값이 흩어지면 첫 페이지 기준이 바뀔 때 일부만 고쳐질 수 있다.
  - `withDefault`에 기본값을 두면 "URL에 값이 없을 때"와 "허용되지 않는 값이 왔을 때"의 폴백이 한 곳에서 정의된다. 읽는 쪽에서 기본값을 다시 보정할 필요가 없다.

## 3. 상수 모듈의 경계 — 계약 상수만 모은다

- 결정: 상품 도메인 상수 모듈에 **계약 상수만** 모은다.
  - 포함: 카테고리 옵션 목록, 정렬 옵션 목록, 상품 페이지 사이즈, 첫 페이지 번호
  - 제외: 카테고리 라벨(`CATEGORY_LABELS`), 정렬 라벨(`SORT_LABELS`) — `ProductListSection.tsx`에 그대로 둔다
  - 모듈은 타입 외에 아무것도 import하지 않는 잎 노드로 유지한다.

- **근거 (1) — 라벨을 계약 상수에서 분리하는 이유**
  - 옵션 목록은 **URL·API 계약**이다. parser의 허용값이자 서버가 검증하는 값이며, 바뀌면 기존 공유 링크가 깨진다. 화면이 없어도 존재해야 하는 값이다.
  - 라벨은 **화면 표시**다. 계약이 그대로여도 문구는 독립적으로 바뀔 수 있다.
  - 두 값은 수명도 다르다. `GET /api/products` 응답에 이미 `categories`(id + name)가 포함되어 있어, 카테고리 라벨은 향후 서버 응답이나 다국어 리소스로 대체될 여지가 있다. 반면 옵션 목록은 클라이언트가 URL을 파싱하기 위해 요청 이전에 알아야 하므로 서버 응답으로 대체할 수 없다.
  - 성격이 다른 둘을 한 모듈에 넣으면 "이 모듈은 무엇을 담는가"가 흐려지고, 라벨을 서버 응답으로 옮길 때 계약 상수까지 함께 흔들린다.
  - 잎 노드로 유지하는 이유: parser 모듈이 이 상수를 import하고, 라벨을 쓰는 컴포넌트도 parser 결과 타입에 의존한다. 상수 모듈이 다른 모듈을 import하기 시작하면 순환 참조가 생기기 쉽다.

## 4. 기본값도 URL에 유지한다

- 결정: `useQueryStates`에 `clearOnDefault: false`를 지정해, 값이 기본값과 같아도 쿼리 파라미터를 제거하지 않는다.
- 결정: 단 `/products` **최초 진입 시 빈 URL은 그대로 감수**한다. 진입 시점에 기본값을 URL에 채워 넣는 정규화는 하지 않는다.

- 근거
  - 파라미터가 항상 드러나 있으면 URL만 보고 목록 필터링 결과를 예측할 수 있다. 공유 링크가 자기설명적이 된다.
  - 발제 요구사항 "API를 호출할 때 기본 정렬도 `sort=latest`로 명시한다"와 방향이 같다.
  - `clearOnDefault: false`는 **세터를 통해 값을 쓸 때** 적용되는 옵션이지, 최초 진입 시 URL을 채워 주지는 않는다. 따라서 사용자가 필터를 한 번도 건드리지 않으면 URL은 비어 있다.
  - 이를 결함이 아니라 의도로 둔다. 파라미터 없는 `/products`는 **"사용자가 아무 탐색 동작도 하지 않은 초기 상태"**라는 의미를 그 자체로 갖는다. 진입만으로 히스토리를 조작해 URL을 바꾸면 사용자가 하지 않은 동작을 한 것처럼 기록이 남는다.

## 5. `q`의 공백 처리 — URL은 원본 보존, 정규화는 요청 경계

- 결정: URL과 검색창 표시값은 사용자가 입력한 표현을 그대로 보존한다. 앞뒤 공백 제거는 현행대로 `toProductListQuery`(URL → 요청 파라미터 변환 지점)에서만 수행한다. parser 단계에서 trim하지 않는다.

- 근거
  - query key가 `toProductListQuery`의 반환값을 싣기 때문에(→ [server-state-design.md](./server-state-design.md) 2번 항목), 정규화가 요청 경계에 있으면 `q=" 나이키"`와 `q="나이키"`가 **같은 캐시 엔트리로 합쳐진다.** URL 표기가 달라도 캐시는 나뉘지 않는다.
  - 서버도 받는 즉시 `trim().toLocaleLowerCase('ko')`를 수행하므로 클라이언트 정규화는 서버 규칙의 선행이지 새로운 규칙이 아니다.
  - 대소문자 소문자화는 **검색 매칭 규칙**이지 상태의 정체성이 아니다. 사용자가 `Nike`로 검색한 표현을 URL에 그대로 남기는 편이 공유·재방문 시 자연스럽다. 같은 이유로 공백도 URL에서는 보존한다.
  - 내부 공백은 어느 지점에서도 축약하지 않는다. 서버 매칭이 `` `${brand} ${name}` ``에 대한 `includes(q)`라서 `나이키  운동화`(공백 2개)는 실제로 다른 검색 결과를 낸다. 내부 공백 축약은 정규화가 아니라 동작 변경이다.

## 6. `page` 범위 보정 — 하한과 상한을 다른 위치에서 처리한다

- 결정

  | 구분                     | 판정에 필요한 것    | 처리 위치                                         | URL 정정                      |
  | ------------------------ | ------------------- | ------------------------------------------------- | ----------------------------- |
  | 하한 `page < 1`          | 값 자체             | parser 전처리 (`createParser`로 감싼 정수 parser) | 하지 않음 — 8번 항목으로 이월 |
  | 상한 `page > totalPages` | 응답의 `totalCount` | `resolvePageOverflow` → `correctPage`             | 함 (`history: 'replace'`)     |

- 결정: `toProductListQuery`의 `page: Math.max(1, filters.page)`를 제거하고, 하한 보정 책임을 parser로 옮긴다.
  → **[server-state-design.md](./server-state-design.md) 2번 항목 "정규화가 필요한 대상"의 `page` 보정 위치를 개정한다.** 보정 규칙(1 이상 정수) 자체와 그로 인한 query key 통합 효과는 그대로 유지되며, 수행 지점만 요청 경계에서 URL 경계로 앞당긴다.

- 결정: `totalCount === 0`이면 상한 보정을 하지 않는다.

- **근거 (2) — 하한과 상한을 다른 위치에서 처리하는 이유**
  - 두 보정은 **판정에 응답이 필요한가**가 다르다. 하한은 URL 값만 보면 즉시 알 수 있고, 상한은 `totalCount`를 받아야 `totalPages`를 계산할 수 있다. 알 수 있는 시점이 다르므로 처리 시점도 갈린다.
  - 하한을 응답 이후로 미룰 수 없는 결정적 이유가 있다. 서버는 무효한 `page`를 보정하지 않고 **400을 반환한다**(`src/app/api/products/route.ts`의 `/^[1-9]\d*$/` 검증). 그리고 `productQueries.list`의 `retry` 정책상 4xx는 재시도하지 않으므로 `useSuspenseQuery`가 곧바로 throw하고 ErrorBoundary가 잡는다. 이때 `ProductListSection`이 렌더되지 않으므로 **보정 effect 자체가 실행되지 않는다.** `?page=0`으로 진입하면 사용자가 URL을 직접 고치지 않는 한 빠져나올 수 없는 에러 화면에 갇힌다.
  - 상한은 이 문제가 없다. `?page=999`는 양의 정수라 서버가 200과 빈 배열을 주고, 렌더가 정상 진행되어 보정 effect가 동작한다.
  - 따라서 하한은 **요청이 나가기 전에** 막아야 하고, 그 유일한 지점이 parser다. 요청 경계(`toProductListQuery`)에 두면 요청은 막을 수 있지만 URL 상태와 화면 표시(`{page} / {totalPages}`)에는 무효값이 그대로 남아 원본이 둘로 갈린다.
  - 부수 효과로 무효한 `page`가 애초에 요청과 query key에 도달하지 않으므로, 실패 응답이 값마다 다른 key로 캐시되는 일도 없어진다.
  - `totalCount === 0`에 보정하지 않는 이유: 결과가 0건이면 유효 페이지 범위 자체가 존재하지 않아 "몇 페이지로 보정할지"에 답이 없다. 빈 결과 화면이 정상적으로 노출되며, 조건을 바꾸면 어차피 첫 페이지로 돌아간다.
  - 하한이 parser에서 걸러지므로 `resolvePageOverflow`는 상한만 담당한다. 함수명과 책임이 일치하며, `totalCount === 0` early return이 하한 판정을 가리는 순서 문제도 발생하지 않는다.

## 7. 히스토리 전략 — 사용자 의도는 `push`, 시스템 보정은 `replace`

- 결정: 기본 `history: 'push'`를 쓰되, `correctPage`(상한 보정)만 `{ history: 'replace' }`로 호출한다.

- **근거 (3) — 보정에만 `replace`를 쓰는 이유**
  - 발제 요구사항상 각 조건 변경은 뒤로 가기·앞으로 가기로 복원되어야 하므로 사용자가 일으킨 변경은 `push`가 맞다.
  - 상한 보정을 `push`로 하면 히스토리가 망가진다. `?page=999` → 보정으로 `?page=3`이 새 엔트리로 쌓이고, 사용자가 뒤로 가기를 누르면 `?page=999`로 되돌아가 다시 보정이 일어난다. 뒤로 가기가 동작하지 않는 것처럼 보이거나 보정이 반복된다.
  - 더 근본적으로, 상한 보정은 **사용자가 하지 않은 동작**이다. 시스템이 잘못된 상태를 바로잡은 것이므로 사용자의 탐색 기록에 남을 이유가 없다. `replace`는 이 의미를 그대로 표현한다.
  - 이 기준은 8번 항목을 재개할 때도 그대로 적용된다. 지원하지 않는 값의 URL 정정 역시 시스템 보정이므로 `replace`다.

## 8. 보류 — 지원하지 않는 값의 URL 정정

- 상태: 보류. 별도 논의 후 결정한다.
- 대상: `category`·`sort`의 허용값 외 입력, `page` 하한 위반
- 현재 동작: parser가 기본값으로 폴백해 **화면과 API 요청은 항상 정상**이지만, URL에는 무효한 값이 그대로 남는다. 새로고침하거나 링크를 공유해도 무효값이 유지된다.
- 쟁점: URL을 원본으로 선언한 이상 URL과 실제 적용값이 다른 상태는 원칙에 어긋난다. 다만 정정하려면 진입 시점에 원본 쿼리스트링과 파싱 결과를 비교하는 처리가 추가로 필요하다.
- 진행 시 유의할 점
  - "URL에 먼저 반영한 뒤 요청한다"는 순서는 실제 동작과 다르다. parser가 렌더 중 동기적으로 폴백값을 주므로 **요청은 처음부터 정규화된 값으로 나가고, URL이 뒤따라 정정된다.** 무효한 값으로 요청이 나가거나 요청이 두 번 발생하지 않는다는 점에서 오히려 이 순서가 낫다.
  - 정정은 시스템 보정이므로 `history: 'replace'`를 쓴다(7번 항목).
- 보류 상태에서 생기는 비대칭: 현재는 `page` 상한만 URL을 정정하고 나머지는 정정하지 않는다. 상한은 응답을 받아야 알 수 있는 값이라 진입 시점 정적 검증과는 애초에 다른 축이므로 모순은 아니며, 이 항목을 재개하면 해소된다.

## 9. 상태 묶음과 API 요청 변환

- 결정: 검색·카테고리·정렬·페이지를 `useQueryStates` **한 묶음**으로 관리한다. 필드별 `useQueryState`를 쓰지 않는다.
- 결정: URL 상태 → `ProductListQuery` 변환은 query 팩토리(`productQueries.list`)에서 호출한다.

- 근거
  - 필드별로 나누면 "카테고리 변경 + 페이지 리셋"이 세터 두 번 호출이 되어 **히스토리 엔트리가 2개** 쌓인다. 사용자는 뒤로 가기를 두 번 눌러야 직전 상태로 돌아가고, 중간 엔트리는 "카테고리는 바뀌었는데 페이지는 아직 이전 값"인 존재한 적 없는 상태다. 한 묶음이면 세터 한 번 = 엔트리 1개라 발제의 뒤로 가기 복원 요구사항과 일치한다.
  - 변환 함수를 query 팩토리에서 호출하면 **query key와 실제 요청 파라미터가 같은 출처에서 나온다.** 둘이 어긋날 수 없다는 것이 이 배치의 핵심 이점이며, 상세 근거는 [server-state-design.md](./server-state-design.md) 2번 항목에 있다.

## 10. 조건 변경 규칙 — 리셋은 훅에 캡슐화, 세터는 partial update

- 결정: "검색·카테고리·정렬이 바뀌면 페이지를 첫 페이지로 되돌린다"는 규칙을 `useProductListFilters` 안에 캡슐화한다. 호출부는 `setCategory(value)`만 알고 페이지가 어떻게 되는지는 모른다.
- 결정: 세터는 **partial update**로 호출한다. `{ ...filters, page }` 형태의 object spread를 쓰지 않는다.

- 근거 — 리셋을 훅에 두는 이유
  - 이 규칙은 UI 이벤트가 아니라 **도메인 불변식**이다. 훅이 URL 상태의 불변식을 지키는 경계 역할을 한다.
  - 필터가 추가될 때(예: 가격대) 새 호출부에서 리셋을 빠뜨려도 타입 검사에 걸리지 않는다. 규칙이 한 곳에 있으면 누락 자체가 성립하지 않는다.
  - 2번 항목에서 `FIRST_PAGE` 상수화를 택한 동기가 "같은 의미의 값이 흩어지는 것"이었다. 리셋을 호출부로 내리면 흩어지는 지점이 오히려 늘어나 그 결정과 어긋난다.
  - ⚠️ **"통합 객체로 관리하므로 분리가 불가능하다"는 근거가 아니다.** partial update이므로 호출부에서 `setFilters({ category, page: FIRST_PAGE })`를 직접 부르는 것도 기술적으로 가능하다. 캡슐화하는 이유는 불가능해서가 아니라 **정책이기 때문**이다.

- 근거 — spread를 쓰지 않는 이유
  - `useQueryStates`의 세터는 넘기지 않은 키를 그대로 유지한다. "나머지 조건 유지"는 spread 없이 이미 보장된다.
  - spread를 쓰면 `useCallback` 의존성에 `filters`가 들어가야 해 **stale closure 위험**이 생긴다. 현재는 의존성이 `[setFilters]`뿐이라 이 위험이 원천적으로 없다.
  - `filters`가 바뀔 때마다 모든 세터가 새 함수가 된다. 상한 보정 effect가 `correctPage`를 의존성에 갖고 있어, 세터가 매번 재생성되면 effect도 매번 재실행된다.
  - 관심 없는 필드까지 URL에 다시 기록된다. 향후 다른 곳에서 관리하는 쿼리 파라미터가 생기면 충돌 지점이 된다.

## 11. 검색어 — 로컬 상태에서 URL로 승격하는 시점

- 결정: 입력 중인 검색어는 컴포넌트 로컬 상태(controlled input)로 두고, **제출 시점에만** URL로 승격한다.
- 결정: 승격 시 페이지를 첫 페이지로 되돌린다(10번 항목의 규칙에 따라 훅 내부에서 처리).
- 결정: 입력할 때마다 URL을 갱신하는 debounce는 후속 작업으로 미룬다.

- 근거
  - 제출 전 입력값은 공유하거나 복원할 대상이 아니다. 발제도 "제출 전 입력값처럼 잠시 머무는 값은 컴포넌트 가까이에 둔다"를 명시한다.
  - 매 입력마다 URL을 바꾸면 `history: 'push'`와 결합해 히스토리가 글자 수만큼 쌓인다. 뒤로 가기가 한 글자씩 되돌아가는 동작이 되어 7번 항목의 히스토리 전략과 충돌한다.
  - 검색어 변경도 목록 조건 변경이므로 페이지 리셋 대상이다. 카테고리·정렬과 같은 규칙을 적용해 예외를 만들지 않는다.

## 12. 미해결 사항

아래 항목은 결정하지 않았다. 각 항목의 현재 동작은 명시된 대로이며, 그대로 두어도 Basic 범위의 완료조건은 충족한다.

### 12-1. 지원하지 않는 값의 URL 정정 (= 8번 항목)

가장 큰 미해결 항목이다. 상세 내용은 [8번 항목](#8-보류--지원하지-않는-값의-url-정정)에 있다. 요약하면, parser가 기본값으로 폴백해 화면과 요청은 정상이지만 URL에는 무효값이 남는다.

### 12-2. `startTransition` 도입 범위

- 쟁점: 필터 변경 중 Suspense fallback 대신 이전 목록을 유지할지.
- 확인된 사실: `nuqs@2.9.0`의 `Options`에 `startTransition`이 있으나, 타입 정의상 1차 목적은 **`shallow: false`인 non-shallow 업데이트에서 Server Component 로딩 상태를 관찰**하는 것이다. 현재는 `shallow` 기본값 `true`(클라이언트 컴포넌트 + `useSuspenseQuery`)라 서버 왕복이 없어, 옵션으로 넘기는 것만으로 얻는 효과가 제한적이다. 목적이 "이전 목록 유지"라면 세터 호출을 transition으로 감싸는 쪽이 직접적이다.
- 참고: `useSuspenseQuery`는 `placeholderData`를 지원하지 않으므로 이 구조에서 기존 목록 유지 수단은 사실상 transition뿐이다.
- 범위: 발제 Advanced C의 "페이지 변경 중 기존 목록 유지"에 해당한다. Basic에 넣을지 Advanced로 미룰지 먼저 정해야 하며, 도입 시 `isPending`을 어떻게 표현할지도 함께 정한다.

### 12-3. 검색 입력창의 리마운트로 인한 포커스 상실

- 현재 동작: `<SearchInput key={filters.q} ... />`로 URL의 `q`가 바뀔 때 입력창을 리마운트해 값을 동기화한다. 뒤로 가기 복원에는 이 방식이 필요하지만, **검색 제출 직후에도 `filters.q`가 바뀌므로 함께 리마운트되어 포커스가 사라진다.** 연속 검색이 끊긴다.
- 선택지: 현행 유지(뒤로 가기 동기화 확보, 포커스 상실 감수) / `key`를 제거하고 뒤로 가기 동기화를 포기.
- 참고: 4번 항목에서 URL을 원본으로 택했으므로 뒤로 가기 동기화를 포기하지 않는 편이 일관된다.

### 12-4. debounce 구현 수단

- 쟁점: 후속으로 debounce를 도입할 때 지연을 어느 지점에 걸지.
  | 수단                                     | 지연 대상              | 입력 중 상태의 원본 |
  | ---------------------------------------- | ---------------------- | ------------------- |
  | 커스텀 훅(`useDebouncedValue`)           | 로컬 state → 세터 호출 | 로컬 state          |
  | `nuqs`의 `limitUrlUpdates: debounce(ms)` | 세터 호출 → URL 반영   | URL(반영만 지연)    |
- 주의: 두 수단을 동시에 쓰면 지연이 이중으로 걸린다.
- 정리 필요: `src/productList/hooks/useDebouncedValue.ts`가 추가되어 있으나 **어디서도 import되지 않는다.** 후속 작업 시점에 되살리고 지금은 포함하지 않는 편이 깔끔하다.

### 12-5. 필터 컴포넌트 배선 방식

- 쟁점: 검색폼·카테고리·정렬·페이지네이션이 URL 상태를 읽고 쓰는 경로.
  | 방식                       | 유리한 점                            | 불리한 점                                   |
  | -------------------------- | ------------------------------------ | ------------------------------------------- |
  | props                      | 자식이 순수해져 테스트·재사용이 쉬움 | 부모가 배선을 모두 알아야 함                |
  | 각 컴포넌트가 훅 직접 호출 | 배선이 사라짐, 필요한 필드만 사용    | 해당 화면 전용이 되어 공통 컴포넌트로 못 씀 |
- 참고: `useQueryStates`는 원본이 URL 하나라 여러 컴포넌트에서 호출해도 값이 항상 일치한다. Context 없이 동기화가 보장되는 것이 URL 상태의 구조적 이점이다.
- 현재 상태: depth 1(`ProductListSection` → `SearchInput`)이라 props로 충분하며, CLAUDE.md의 "Props Drilling 3단계 이상이면 Context 검토" 기준에 걸리지 않는다. **필터를 독립 컴포넌트로 분리할 계획이 있는지가 갈림길이다.**

### 12-6. 그 밖에 확인만 하고 넘긴 것

논의 결과 별도 결정이 필요하지 않다고 판단했으나, 판단 근거를 남긴다.

- **`q`의 `clearOnDefault` 예외**: 4번 결정에 따라 검색어를 비우면 URL에 `?q=`가 남는다. `withOptions({ clearOnDefault: true })`로 `q`만 예외를 둘 수 있다. 다른 세 필드는 기본값 자체가 의미 있는 선택지(전체/최신순/1페이지)지만 `q`의 빈 문자열은 선택지가 아니라 입력 없음이라는 차이가 있다. 현재는 규칙 통일을 우선해 예외를 두지 않는다.
- **`shallow` 옵션**: 기본값 `true`를 유지한다. 클라이언트 컴포넌트 + TanStack Query 구조라 URL 변경 시 서버가 다시 실행될 이유가 없다. Advanced B(서버 프리패치)를 선택하면 `shallow: false`가 필요해지므로 그때 재검토한다.
- **parser 모듈과 상수 모듈의 분리**: 3번 결정("상수 모듈은 잎 노드")의 귀결로, parser는 `nuqs`를 import하므로 상수 모듈과 파일을 분리하는 편이 일관된다.
- **`scenario` 파라미터**: `useQueryStates`는 맵에 선언한 키만 조작하므로 세터를 거쳐도 URL에 보존된다. 발제의 "URL 상태에 넣지 않는다"와 충돌하지 않는다.
- **`urlKeys` 단축 키**: 4번에서 URL 가독성을 우선했으므로 도입 이유가 없다.
- **`parseAsIndex`**: 1-based URL ↔ 0-based state 변환용인데 서버도 1-based라 변환할 것이 없다.
