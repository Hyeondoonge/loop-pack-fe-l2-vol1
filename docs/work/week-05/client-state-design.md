# 5주차 상태 설계 의사결정 기록 — 클라이언트 상태(Zustand) 설계

> 대상: 비로그인 사용자의 장바구니·위시리스트(로컬 익명 상태)
> 배경: [state-design.md](./state-design.md) 3·4번 항목에서 소유자를 클라이언트(Zustand)·저장 형태를 `Set<string>`으로 정한 뒤, store 단위의 세부 결정을 별도 문서로 분리.
> 연관: [server-state-design.md](./server-state-design.md), [url-state-design.md](./url-state-design.md) — 같은 값을 세 상태에 중복 저장하지 않는다는 경계를 공유한다.
> 표기: 이 문서는 설계 논의를 AI로 정리한 초안이며, 결정 내용과 근거는 직접 검토했다.

## 전제 — 요구사항 제약

| 요구             | 의미                                                                   |
| ---------------- | ---------------------------------------------------------------------- |
| 최소 데이터 저장 | 서버 `Product` 전체를 store에 복사 금지. 상태 판별에 필요한 것만       |
| 개수는 파생      | 헤더 개수를 별도 상태로 두지 않고 ID 집합에서 계산                     |
| selector 경계    | 헤더는 개수만, 상품 버튼은 해당 상품 포함 여부 + action만 구독         |
| 상태 일치        | 홈·목록의 같은 상품이 같은 담김·찜 상태로 보임                         |
| 이동 중 유지     | 클라이언트 페이지 이동 시 상태 유지 (새로고침 초기화는 허용)           |
| 중복 저장 금지   | 같은 값을 서버 상태·URL 상태·Zustand에 중복 저장하지 않음              |

**범위 밖(구현하지 않음)**: 장바구니 상세 페이지, 상품 수량, 합계 금액, `persist`, 서버 mutation·낙관적 업데이트.

## 0. 가격 포맷 — 로케일 미지정으로 인한 hydration 불일치

### 문제

`ProductListSection.tsx`가 상품 가격을 `product.price.toLocaleString()`으로 로케일 인자 없이 포맷한다.

- 인자 없는 `toLocaleString()`은 런타임 기본 로케일을 따른다. 서버(Node)와 브라우저의 기본 로케일·ICU 데이터가 다르면 천 단위 구분 기호가 달라져 서버 HTML과 클라이언트 렌더 결과가 어긋난다.
- 지금은 `useSuspenseQuery`가 서버에서 suspend되어 가격이 SSR되지 않아 드러나지 않는다. 서버 프리패치를 붙이면 가격이 서버에서 렌더되기 시작하면서 hydration 불일치로 표면화된다.
- 홈을 실제 데이터로 구현하면 가격 표시 지점이 늘어난다. 복제되기 전이 고칠 시점이다.

### 결정

상품 가격 표시를 공통 유틸(`formatPrice`)로 통일하고, 로케일을 명시한다.

### 근거

가격 표시는 상품 가격·할인 가격·장바구니·결제 내역 등 여러 컴포넌트에서 쓰인다. 통화 기호와 단위(`원`) 정책까지 한 곳에 모을 수 있다.

## 1. store 구성 단위 — 장바구니와 위시리스트를 한 store에 둘까

### 문제

두 상태는 자료구조가 동일(상품 ID 집합)하고 헤더에 나란히 표시된다. 한 store의 두 slice로 둘지, 별도 store 2개로 둘지.

### 결정

**별도 store 2개.**

### 근거

- 서로 다른 도메인이다. 둘을 묶는 공통 store에 붙일 이름부터 애매해진다(이름이 안 나온다는 것은 응집이 없다는 신호).
- 함께 수정되어야 하는 컴포넌트가 없다. 한쪽 변경이 다른 쪽을 건드리지 않는다.

---

## 2. 저장 자료구조 — ID를 무엇으로 담을까

### 문제

`string[]` / `Set<string>` / `Record<string, true>` 중 선택. 이 결정이 포함 여부 조회 비용, 개수 파생 방식, selector 안정성을 동시에 좌우한다.

- 조회 비용: 배열 `includes`는 O(n), Set·Record는 O(1)
- 개수 파생: 배열 `.length`, Set `.size`, Record `Object.keys().length`
- 불변성: Zustand는 참조 교체로 갱신을 감지하므로 Set이면 매 토글마다 새 Set을 만들어야 한다. selector가 boolean·number 같은 원시값을 반환하는 한 참조 문제는 없다.

### 결정

**`Set<string>`.**

### 근거

포함 여부 조회가 O(1)로 빠르고, 중복이 자료구조 차원에서 방지된다.

## 3. store 생성·제공 방식 — 모듈 전역 vs Context Provider

### 문제

모듈 스코프에서 `create`로 만들지, Provider로 감싸 요청별 인스턴스를 만들지. 세 가지에 영향이 있다.

- **SSR 오염**: 모듈 전역 store는 서버에서 요청 간 공유될 수 있다.
- **페이지 이동 유지**: layout에 Provider를 두거나 모듈 전역이면 클라이언트 네비게이션 중 유지된다.
- **테스트 격리**: 모듈 전역은 테스트 간 상태가 새어 초기화 처리가 필요하다.

### 결정

**모듈 전역 store.**

### 근거

1. 클라이언트 컴포넌트에서만 조작되므로 서버 프로세스의 인스턴스는 빈 상태를 유지한다. 이를 전제로 설계했으므로, 서버 렌더 경로에서 store를 읽거나 쓰는 것을 제한한다.
2. 자바스크립트 런타임당 인스턴스 1개(싱글톤). 앱에 장바구니는 하나뿐이라 Provider의 인스턴스 다중화가 필요 없고, 오히려 React 밖에서 `getState()`로 접근할 수 있는 이점이 있다.
3. 2번 때문에 Provider의 보일러플레이트(약 30줄)와 "Provider 누락 시 런타임 에러"라는 실패 모드는 대가 없는 비용이 된다.

### 남는 조건

`persist`나 서버 프리패치를 도입하면 1번 전제가 깨진다. 그때 Provider 방식을 다시 검토한다.

## 4. Header 추출 범위 — 어디에 두고 무엇을 구독할까

### 문제

헤더 마크업이 홈·목록 예시에 각각 static으로 중복돼 있고(`위시리스트 0`, `장바구니 0`), `app/layout.tsx`에는 없다. 개수를 상태에서 구독하려면 클라이언트 헤더가 필요하다. 공용 컴포넌트로 추출할지, 어느 레이아웃에 올릴지.

### 결정

`layout.tsx`에 헤더(내비게이션 바)를 배치하고, 헤더가 개수를 직접 구독한다.

### 근거

모든 페이지에서 동일하게 쓰이는 전역 컴포넌트다. 페이지마다 두면 중복 마크업과 중복 구독이 그대로 남는다.

## 5. 홈 실연동 범위 — 이번 단계에서 어디까지

### 문제

완료 조건인 "홈에서 담은 상품이 목록에서도 담긴 상태로 보인다"를 만족하려면 홈도 실제 상품 데이터와 담기·찜 버튼이 필요하다. 그런데 홈은 아직 static 예시(`HomeLayoutExample.tsx`)이고, 이는 서버 상태 구현 범위와 겹친다. `homeQueries.ts`는 이미 작성돼 있으나 홈 페이지가 아직 호출하지 않는다.

### 결정

홈·목록 페이지 모두에 담기·찜 이벤트 핸들러를 추가한다. 홈 서버 상태 연동은 원래 누락된 작업이므로, 클라이언트 상태 설계 기반 구현 직후 별도 작업으로 진행한다.

### 근거

같은 상품을 두 페이지에서 토글해 상태 일치를 실제로 검증해야 완료 조건이 성립한다. 다만 서버 상태 연동과 클라이언트 상태 구현을 한 커밋에 섞지 않는다.

## 6. 담기·찜 버튼의 컴포넌트 경계와 계약

### 문제

버튼은 서버에서 온 `Product`를 받는 위치에 있지만 store에는 ID만 넘겨야 한다(최소 데이터 원칙). 버튼이 받는 prop을 `productId`만으로 할지, `Product`를 통째로 받아 내부에서 ID를 추출할지.

### 결정

트리거 시 전달하는 핸들러 계약은 **상품 ID만** 넘긴다.

### 근거

핸들러가 상품 전체 정보를 필요로 하지 않는다. 필요한 정보만 전달하면 핸들러의 동작을 예측하기 쉽고, `Product` 전체를 넘겼을 때 생기는 "store에 복사해도 되나" 하는 여지 자체가 사라진다.

## 7. action 계약 — toggle 하나 vs add/remove 분리

### 문제

버튼이 `aria-pressed`로 토글되므로 `toggle(id)` 하나로 충분한가, 아니면 `add`/`remove`를 분리해 호출부에서 의도를 명시할까.

### 결정

`toggle`, `add`, `remove` 모두 제공한다.

### 근거

에러 발생 시 원래 상태로의 복구를 명시적으로 수행하기 위해서다. 복구를 `toggle` 재호출로도 할 수 있지만, 그것은 "현재 상태의 반대"라는 간접 표현이다.

- `toggle` — 사용자 동작(버튼 클릭)을 위한 계약
- `add`/`remove` — 프로그램 코드에서 목표 상태를 명시적으로 지정하기 위한 계약

## 8. 향후 로그인 동기화 대비 — 지금 설계에 무엇을 남길까

### 문제

로그인·서버 동기화가 생기면 장바구니·위시리스트의 원본이 서버로 이동한다. 그때 익명 상태를 계정 데이터에 병합할지·버릴지·충돌을 어떻게 처리할지 정해야 한다. Basic에서는 구현하지 않되, 지금 store 경계를 어떻게 그으면 전환이 쉬운지만 정리한다.

### 결정 (방향만)

병합 방향은 **비로그인 상태에서 쌓은 데이터를 유지하는 쪽**을 선호한다. 구체적인 충돌 처리 규칙은 미확정.

### 지금 설계가 전환에 남기는 것

- store에 ID만 두었으므로(2번), 서버 장바구니로 옮길 때 넘길 데이터가 ID 목록 하나로 끝난다.
- 상품 정보는 서버 상태가 소유하므로(state-design.md 3번), 소유권이 서버로 이관돼도 클라이언트에 남은 중복 데이터가 없다.

### 미해결

- [ ] 병합·폐기·충돌 처리 규칙
- [ ] 이관 후 Zustand의 역할 재정의(서버 상태의 임시 입력인지, 순수 UI 상태인지)

## 9. 헤더가 개수 2개를 구독하는 방식

### 문제

헤더는 장바구니·위시리스트 **두 개**의 개수를 함께 표시한다. 훅을 두 번 호출할지, 한 번에 객체로 반환할지.

| 방식                                                     | 특징                                                                                             |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 훅 2회 — `useCartStore(s => s.items.size)` + 위시리스트  | 각각 number를 반환해 참조 비교 문제가 없다                                                       |
| 객체 1회 — `s => ({ cart: ..., wishlist: ... })`         | 매 렌더 새 객체가 생성된다. Zustand v5는 selector 결과에 기본 얕은 비교를 적용하지 않으므로 값이 그대로여도 리렌더된다 (`useShallow` 필요) |

### 결정

**훅을 두 번 호출한다.**

### 근거

객체 반환 방식은 매 렌더 새 객체를 만들어 `useShallow` 없이는 불필요한 리렌더가 발생한다. 1번 결정(별도 store 2개)과도 자연스럽게 맞는다 — 애초에 서로 다른 store라 한 번에 묶어 읽을 수 없다.

## 10. action을 어떻게 가져올 것인가 — selector 구독 vs `getState()`

### 문제

action 함수는 store 생성 후 참조가 바뀌지 않으므로 selector로 구독해도 리렌더를 유발하지 않는다. 그렇다면 이벤트 핸들러 안에서 `useCartStore.getState().toggle(id)`로 직접 부르는 방식과 무엇이 다른지, 어느 쪽을 규칙으로 삼을지.

### 결정

**selector로 구독한다.**

### 근거

상태 조회와 action 조회의 접근 방식을 하나로 유지한다. 두 방식이 섞이면 "이 값은 왜 저 방식으로 가져오나"를 매번 판단해야 한다. action은 참조가 고정이라 selector 구독의 비용이 사실상 0이므로, 일관성을 택하는 데 드는 대가가 없다.

## 11. store 코드의 배치 위치

### 문제

현재 코드는 기능 폴더(`src/productList/`) + API 계층(`src/app/api/{domain}/`) 구조다. 장바구니·위시리스트 store는 홈·목록·헤더가 함께 쓰므로 `productList` 하위에 두면 소유가 어긋난다. 새 기능 폴더를 만들지, 공용 store 디렉터리를 둘지.

### 결정

`app/store/wishlist`, `app/store/cart`.

### 근거

1계층은 역할(기술 계층: store), 2계층은 도메인(cart·wishlist)으로 나눈다. 기존 `src/app/api/{domain}/` 구조와 같은 원칙 — 계층으로 먼저 나누고 그 안을 도메인으로 나누는 방식을 그대로 따른다.

## 12. 카테고리 상태 SSOT — 검증용 ID와 표시용 이름의 분리

> 관련: [Week 05 · 카테고리 상태 SSOT 설계 의사결정](https://app.notion.com/p/3a6a513da61e815f921bd7e3cf3de328) — A/B 두 갈래를 검토한 논의 전체.

### 문제

`ProductListSection.tsx`의 카테고리 select가 `CATEGORY_OPTIONS`(client 정적 상수)와 `CATEGORY_LABELS`(client 하드코딩 이름 맵) 두 가지로 그려진다. 그런데 `categories`는 서버가 소유한 데이터(`ProductListResponse.categories`, `HomeResponse.categories`)다. 홈은 이미 서버 응답으로 그리는데 목록만 client 상수로 그려 두 화면이 같은 값을 서로 다른 출처에서 읽는 SSOT 위반이었다.

"categories"는 실제로 두 겹이다:

| 겹 | 정체 | 위치 |
| --- | --- | --- |
| 유효 ID 집합 | 고정 계약 enum(`all\|casual\|fashion\|goods\|home\|digital`) | `CATEGORY_OPTIONS` |
| 표시 이름 | `{id, name}[]` | 서버 응답 `categories` |

ID 집합은 `docs/assignments/week-05.md`(103·110·116행)가 못박은 **API 계약**이다 — 잘못된 category는 지연 없이 HTTP 400. 이 값을 서버 fetch로 옮기면(A안) `url-state-design.md` §6이 이미 `page` 하한에서 확정한 원칙과 충돌한다: "400을 유발할 값은 parser 단계에서 선행 차단한다." parser는 fetch보다 먼저 도는데, 검증 기준을 fetch 결과에 의존시키면 그 선행 차단이 불가능해지고 필터 바까지 query 에러 경계 안에 들어가야 해 복구 경로가 사라진다.

### 결정

**중복만 제거한다(B안).** ID 집합은 공유 상수(`CATEGORY_OPTIONS`)로 유지하고, 서버 검증(`route.ts`)·URL parser(`productListFilters.ts`)·client 화면 셋 다 이 하나의 상수를 계약으로 삼아 참조한다. `CATEGORY_LABELS`(표시 이름)만 제거하고, 카테고리 라벨은 서버 응답의 `category.name`으로 렌더링한다.

### 근거

- ID 집합은 `SORT_OPTIONS`와 동급인 **계약 상수**다. category·sort·page·pageSize 넷 다 계약 enum/제약이고 `q`만 자유 문자열이다 — category만 서버 fetch로 옮기고 sort는 그대로 두는 건 일관성이 없다.
- 계약이 enum을 고정하고 400을 강제하는 상황에서 "서버가 런타임에 카테고리를 추가/삭제해도 무배포 반영"이라는 A안의 이점이 성립하지 않는다. 대신 A안은 (1) YAGNI로 미뤄둔 카테고리 전용 API 분리를 되살리고, (2) 첫 로드 시 categories→list 직렬 요청을, (3) invalid category를 서버 응답 이후 보정하는 gate 코드를 요구한다 — 대가만 있고 얻는 것이 없다.
- 진짜 SSOT 위반은 표시 이름(`CATEGORY_LABELS`)이었지 검증 ID 집합이 아니었다. 위반의 정확한 지점만 고친다.

### 범위 밖 / 남는 조건

- 카테고리가 실제로 서버에서 런타임에 바뀌는 요구가 생기면 그때 A안(서버 fetch 기반 검증)을 재검토한다.
- `SORT_OPTIONS`도 같은 논리로 이미 공유 계약 상수이므로 추가 변경 없음.
