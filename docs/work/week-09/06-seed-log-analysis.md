# week-09 시드 로그 분석 리포트

- 대상: `fixtures/events-30d.jsonl` (2026-07-22 ~ 2026-08-20, 30일)
- 목적: `docs/rfc/week09-e2e-scope.md` B절(시드 로그 분석)·C절(붙일 곳/안 붙일 곳)을 채우기 위한 **집계 결과와 사실 정리**
- 범위 밖: B절 표의 "E2E 여부(가설)" 칸과 C절 판단은 채우지 않는다. 과제 103번 줄 — "3단계 표를 AI가 채웠다면 그건 본인 판단이 아닙니다". 이 문서는 판단에 쓸 숫자와 근거만 제공한다.
- 재현: 부록의 스크립트를 레포 루트에서 `node analyze.mjs`로 실행하면 같은 숫자가 나온다.

## 1. 판단 기준 정리 (과제 + 멘토 노트)

### 1-1. E2E를 붙일지 정하는 순서 (멘토 노트 "마무리" 표)

| 순서 | 질문 | 판단 재료 | 아니면 |
| --- | --- | --- | --- |
| ① 빈도 | 사용자가 그 경로를 지나가나 | 로그의 **세션 비율** (이벤트 수가 아님) | 계측을 먼저 넣는다 |
| ② 실패 비용 | 깨지면 다른 기능까지 막히나, 돈이 걸리나 | 로그의 실패 이벤트 비율 + 뒤따라 막히는 기능 | 빈도가 낮아도 붙인다 |
| ③ 재현 난이도 | 통합 테스트(jsdom + MSW)로 같은 것을 확인할 수 없나 | 브라우저가 있어야 성립하는가 | 통합 테스트로 내린다 |
| ④ 포기 목록 | 무엇을 안 붙였나 | 안 붙인 흐름과 이유 | 목록을 기록한다 |

멘토 노트가 강조한 두 가지 함정:
- **빈도 1위 ≠ E2E**. 1위 경로가 8주차 통합 테스트로 이미 검증됐다면 "같은 것을 100배 비싼 도구로 다시 확인하는 것"이다.
- **③을 가장 자주 빠뜨린다**. "통합 테스트로 안 되는 이유"를 못 대면 E2E로 만들 이유도 없다.

### 1-2. jsdom에서 확인할 수 없는 것 (③의 구체 목록)

실제 레이아웃 · 쿠키 속성(`httpOnly`·`SameSite`) · 서버 리다이렉트(미들웨어 302) · 초기 HTML(JS 실행 전) · 포커스/키보드/브라우저별 차이.

인증에서는 "로그인 폼 → 쿠키 발급", "미로그인 → 리다이렉트 → `next` 복원", "SSR 초기 HTML 로그인 상태", "세션 만료 안내"가 여기 해당한다. 반대로 "비밀번호 틀렸을 때 에러 표시", "로그인 후 헤더 변경"은 통합 테스트 레벨이다.

### 1-3. 과제가 B절에 요구하는 것 (172~179번 줄)

- 경로는 이벤트 단위든 화면 단위로 묶든 되지만 **묶은 기준**을 적는다
- **세션 기준** 순위
- 비율의 **분모**를 밝힌다 (전체 / 노이즈 제거 후 / 앞 단계 통과 세션)
- 이탈률 **정의**를 고른다 (세션의 마지막 이벤트였던 비율 vs 다음 단계 미도달 비율)
- 실패 비용: 무엇을 **실패 이벤트**로 셌는지 + 막히면 뒤따라 막히는 것
- 봇·오류·중복을 **어떤 기준으로** 걸렀는지
- 걸러내기 **전후 순위 비교**. 안 바뀌었으면 왜 안 바뀌었는지

### 1-4. 과제가 C절에 요구하는 제약 (183~188번 줄)

- 인증 플로우 필수 (= "빈도 낮은데 붙인 경로")
- 인증 외 **2개 이하**, 0개도 답이지만 이유 필요
- 빈도 높은데 안 붙인 경로 1개 이상 + 통합으로 충분한 이유
- 시나리오 하나의 유지보수 비용 추정 (문구/구조 변경 시 고칠 곳 수)
- 로그에 있지만 내 앱에 화면이 없는 경로는 자연히 제외, 이유만 남긴다

구조적 특징 (분석 해석에 영향):
- **한 세션 안에서 같은 이벤트 이름이 두 번 나오는 경우가 없다** (중복 전송 줄 제외). 따라서 이 시드에서는 "이벤트 수 기준"과 "세션 수 기준" 순위가 **같다**. 실서비스 로그에서 두 기준이 갈리는 이유(정렬 5번 바꾼 한 사람)가 이 시드엔 없다. RFC에 "세션 기준으로 셌고, 시드 특성상 이벤트 기준과 동일했다"고 적어야 함.
- 퍼널이 엄격히 선형이다. `login_start`가 있는 세션은 예외 없이 `cart_add` 뒤에 나오고(담기 없이 로그인한 세션 0), `cart_add`는 예외 없이 `product_detail_view` 뒤에 나온다(상세 없이 담기 0), `order_start`는 예외 없이 `login_success` 뒤에 나온다.
- 시드 로그의 흐름: `목록 → (필터·정렬·페이지) → 상세 → (위시리스트) → 담기 → 로그인 → 주문서 → 주문 완료`. 마이페이지·주문 내역·장바구니 화면 진입 이벤트는 **없다**.

## 3. 노이즈 판별 기준과 근거

> ⚠️ **AI 판단 — 검토 필요**: 아래 3-1~3-3의 필터링 기준(무엇을 봇/중복/오류로 볼지)은 AI가 데이터를 근거로 골라 정한 것이다. 과제 177행이 요구하는 "어떤 기준으로 걸렀는지"는 본인이 직접 검토해서 동의/수정해야 한다. **검토를 마쳤다면 이 문구를 지운다.**

### 3-1. 봇 세션 — `device === null`인 세션 486개 (전체 세션의 6.1%)

`device` 값 자체가 봇 표시는 아니지만, null인 줄을 모아 보면 사람 트래픽과 다른 특징이 겹친다.

| 특징 | 관측값 | 사람 트래픽 |
| --- | --- | --- |
| 세션 길이 | 486개 전부 이벤트 1개 | 단일 이벤트 세션은 사람 세션에도 1,135개 있음 (아래 참고) |
| 이벤트 | 전부 `product_list_view`, props 전부 `{category:"all", sort:"latest", page:1}` (기본값 진입) | 다양 |
| 타임스탬프 밀리초 | 486개 전부 `.000Z` (초 단위 정각) | `.000Z`는 21,941줄 중 27줄 — 우연 수준(약 0.1%) |
| 발생 시각 | 486개 전부 UTC **01시대**, 30일 매일 | 하루 종일 분산 |
| 발생 간격 | 같은 날 안에서 수 초~수 분 간격으로 연속, 날짜 사이 간격은 약 85,500초(≈23.75시간) | — |

→ "기본 URL로 매일 새벽 정해진 시간에 한 번씩 첫 페이지만 긁고 나가는 크롤러"로 해석. 네 특징이 모두 겹치는 집합이 `device === null` 집합과 정확히 일치하므로, 필터 조건은 `device === null` 하나로 충분하다.

주의: 사람 트래픽에도 `product_list_view` 하나로 끝난 세션이 1,135개(mobile 382 · desktop 377 · tablet 376) 있다. **"이벤트 1개 = 봇"으로 거르면 안 된다.** 이건 목록만 보고 나간 진짜 이탈이다.

### 3-2. 중복 전송 — 완전 동일한 줄 77개

- 판별: `sessionId · ts · name · props · device`가 모두 같은 줄 (JSON 직렬화 문자열 동일). 밀리초까지 같은 `ts`이므로 "빠르게 두 번 누른 것"이 아니라 전송 계층 중복이다.
- 어떤 이벤트가 중복됐나: `product_list_view` 28 · `page_change` 23 · `category_filter_change` 21 · `sort_change` 5 — **전부 목록 화면 이벤트**. 담기·로그인·주문 쪽 중복은 0.
- 처리: 한 줄만 남긴다. 세션 기준 집계에서는 어차피 세션당 1회로 세므로 순위에 영향 없음. 이벤트 수 기준 집계에는 영향(목록 이벤트만 부풀림).

### 3-3. 오류 이벤트 — `client_error` 103줄 (세션 103개, 노이즈 제거 후 세션의 1.4%)

- 코드는 전부 `IMAGE_LOAD_FAILED`, props에 `productId` 있음.
- 위치: 103건 **전부 `product_detail_view` 직후**. 직후 이벤트는 세션 종료 68 · `cart_add` 26 · `wishlist_add` 9.
- 행동에 영향이 있나: 오류 세션의 상세→담기 전환율 29.1% vs 비오류 세션 28.1%. **차이 없음**. 이미지 로드 실패가 구매 행동을 막지 않는다.
- 처리: **경로 집계에서 제외**(사용자 행동이 아님), **실패 비용 항목에서는 별도 집계**(상세 화면의 오류율 103/4,656 = 2.2%). 세션 자체를 버리지는 않는다 — 오류가 있어도 나머지 이벤트는 정상 행동이다.

### 3-4. 걸러낸 뒤 남는 것

| | 걸러내기 전 | 후 |
| --- | --- | --- |
| 이벤트 | 22,427 | 21,761 (봇 486 · 중복 77 · 오류 103 제거) |
| 세션 | 8,000 | **7,514** (봇 세션 486 제거) |

이하 모든 비율의 **기본 분모는 7,514** (노이즈 제거 후 전체 세션). 다른 분모를 쓰면 그 자리에 적는다.

> ⚠️ **AI 판단 — 검토 필요**: 분모를 7,514(노이즈 제거 후 전체 세션)로 고정한 것은 AI의 선택이다. 과제 174행이 요구하는 "분모를 밝히는 것"은 본인이 직접 정해야 한다. **검토를 마쳤다면 이 문구를 지운다.**

## 4. 세션 기준 순위 — 걸러내기 전후 비교

| 순위 | 이벤트 | 전 (세션 8,000) | 후 (세션 7,514) | 순위 변동 |

**순위가 바뀌지 않은 이유** (과제 178번 줄이 요구하는 항목):
1. 봇 486세션이 **전부 `product_list_view` 1개짜리**라, 이미 1위이고 모든 세션에 있는 이벤트만 부풀렸다. 다른 이벤트의 세션 수는 1도 안 변했다. 분모만 줄어 2위 이하의 **비율은 전부 올라갔다** (상세 58.2→62.0%).
2. 중복 77줄은 세션 기준 집계에서 원래 영향이 없다 (같은 세션의 같은 이벤트는 1회로 센다).
3. `client_error`는 원래 꼴찌라 빠져도 순서가 안 바뀐다.
4. 시드에 세션 내 반복 이벤트가 없어 이벤트 수 기준으로 세도 순위가 같다. 즉 이 시드는 "이벤트 수로 세면 부풀려진다"는 함정을 **재현하지 않는다**. 과제가 세션 기준을 요구하는 이유는 여전히 유효하지만, 이 데이터로는 그 차이를 보여줄 수 없다는 점을 RFC에 적는 편이 정직하다.

| 로그인 시작 | 644 | 0% | 9.0% (58 — 성공 못 함) |

두 정의가 갈리는 곳:
- **목록 진입**: A 15.2% vs B 38.0%. 차이 22.8%p는 "목록에서 필터·정렬·페이지를 만지다 나간 세션" — 마지막 이벤트가 `category_filter_change`(784)·`page_change`(664)·`sort_change`(266)인 세션들이다. 정의 A는 이들을 목록 이탈로 안 세고, B는 센다.
- **상세 진입**: A 64.5% vs B 71.9%. 차이는 상세에서 위시리스트만 추가하고 나간 345세션 (마지막 이벤트가 `wishlist_add`).
- **로그인 시작**: A는 0% — `login_start`가 세션의 마지막인 경우가 없다 (항상 성공이나 실패가 따라옴). 실패로 끝난 58세션은 마지막 이벤트가 `login_fail`이다. 정의 A로 로그인 이탈을 보려면 `login_fail`을 마지막으로 하는 세션을 따로 세야 한다.
- 담기 이후는 두 정의가 같다 (부수 이벤트가 없어서).

멘토 노트 예시(상세 44% 이탈, 담기 후 53%, 주문서 31%)와 비교하면 이 시드에서는 상세 이탈이 더 크고(A 64.5%), 담기 후 이탈(50.8%)과 주문서 이탈(33.9%)은 비슷하다.

## 7. 실패 비용 재료

과제 176번 줄: 실패로 볼 이벤트를 직접 정하고, 비율과 함께 "이 화면이 막히면 뒤따라 막히는 것"을 쓴다. 로그에서 실패로 셀 수 있는 후보는 세 가지.

## 10. 판단에 앞서 확인할 사실 (C절용, 결론 아님)

세 축(빈도 · 실패 비용 · 재현 난이도)에 대응하는 **사실**만 적는다.

- **빈도 상위 2개(목록 진입, 목록 조작)는 8주차 통합 테스트가 이미 덮은 영역이다.** `productListParsers` 단위 테스트, URL 상태·MSW 기반 통합 테스트가 있다. 과제 190번 줄의 "빈도 1위니까 E2E"에 해당하는 자리. 이 두 경로에서 브라우저가 있어야만 확인되는 것이 무엇인지(있다면) 적어야 E2E 제외 근거가 선다.
- **빈도 2위(상세 진입)는 화면이 없다.** 제외 근거는 로그가 아니라 구현 부재.
- **로그인은 빈도 8.6%로 낮지만 로그에서 확인되는 실패 비용이 가장 크다.** 로그인 없는 주문 0건. 실패율 18.8%는 13종 중 가장 높은 실패 비율. 재현 난이도: 미들웨어 302·`next` 복원·쿠키 속성·초기 HTML은 jsdom에 없다 (멘토 노트 PART 2). 과제가 필수로 지정한 이유와 로그가 일치한다.
- **주문(주문서→완료)은 빈도 5.6%, 돈이 걸린 유일한 경로, 미완료 33.9%.** 재현 난이도 측면에서 "통합 테스트로 안 되는 것"이 무엇인지가 판단의 갈림길: 주문 API 호출과 완료 화면 렌더는 MSW로 되지만, 보호 경로(`/orders/new`)에 로그인 상태로 진입하는 부분은 인증 E2E와 겹친다. 인증 시나리오 안에 "복원 경로 = `/orders/new`"로 묶으면 별도 E2E 없이 덮이는지, 주문 제출까지 넣어야 하는지는 직접 정할 항목.
- **담기(17.4%)는 로그의 3번째 큰 전환점이지만 실패 이벤트가 없고, 앱에서는 Zustand 클라이언트 상태다.** 8주차에 store 격리·URL 상태 테스트로 다룬 영역. 브라우저가 필요한 부분(예: 새로고침 후 유지 여부 = 스토리지 persist)이 있는지에 따라 갈린다.
- **마이페이지·주문 내역·장바구니 화면 진입은 로그에 없다.** 빈도 축을 쓸 수 없고, 실패 비용·재현 난이도로만 판단해야 한다 (멘토 노트 QNA "신규 기능은 로그가 없어요").
- **유지보수 비용 추정 대상**으로 인증 시나리오를 고르면, 로그인 폼 라벨(이메일·비밀번호·로그인 버튼), 로그아웃 버튼, 주문서 heading 등 셀렉터가 닿는 곳을 세면 된다. 멘토 노트 예시 테스트(341~359번 줄)는 라벨 2개 + 버튼 1개 + heading 1개 + URL 패턴 2개.

## 부록. 집계 스크립트

레포 루트에서 `node analyze.mjs`. 3절의 필터 세 가지가 상단에 있다.

```js
import fs from "node:fs";
const raw = fs.readFileSync("fixtures/events-30d.jsonl","utf8").trim().split("\n").map(JSON.parse);
const count=(a,k)=>a.reduce((m,x)=>(m[k(x)]=(m[k(x)]||0)+1,m),{});
const group=(a)=>{const m={};for(const e of a)(m[e.sessionId]??=[]).push(e);return Object.values(m).map(s=>s.sort((x,y)=>x.ts<y.ts?-1:1));};
const pct=(n,d)=>d?`${(100*n/d).toFixed(1)}%`:"-";

// 노이즈 필터
const isBot=e=>e.device===null;                                  // 1) 봇: device null
const seen=new Set(); const dedup=[];                             // 2) 중복: 완전 동일 줄
for(const e of raw){const k=JSON.stringify(e);if(!seen.has(k)){seen.add(k);dedup.push(e);}}
const clean=dedup.filter(e=>!isBot(e));
const events=clean.filter(e=>e.name!=="client_error");          // 3) 오류: 경로 집계에서 제외

const sess=group(events); const N=sess.length;
const has=(s,n)=>s.some(e=>e.name===n);

// 세션 기준 순위
const rank=count(sess.flatMap(s=>[...new Set(s.map(e=>e.name))]),x=>x);
console.log(Object.entries(rank).sort((a,b)=>b[1]-a[1]).map(([n,c])=>`${n}\t${c}\t${pct(c,N)}`).join("\n"));

// 퍼널 + 이탈률(A: 마지막 이벤트, B: 다음 단계 미도달)
const steps=["product_list_view","product_detail_view","cart_add","login_start","login_success","order_start","order_complete"];
steps.forEach((st,i)=>{
  const reached=sess.filter(s=>has(s,st)); const next=steps[i+1];
  const lastHere=reached.filter(s=>s.at(-1).name===st).length;
  const noNext=next?reached.filter(s=>!has(s,next)).length:0;
  console.log(`${st}\t도달 ${reached.length} (${pct(reached.length,N)})\tA ${pct(lastHere,reached.length)}\tB ${pct(noNext,reached.length)}`);
});

// 실패 재료
const ls=sess.filter(s=>has(s,"login_start")), lf=ls.filter(s=>has(s,"login_fail"));
console.log(`login_fail ${lf.length}/${ls.length} (${pct(lf.length,ls.length)}), 실패로 종료 ${lf.filter(s=>!has(s,"login_success")).length}`);
const os=sess.filter(s=>has(s,"order_start"));
console.log(`order 미완료 ${os.filter(s=>!has(s,"order_complete")).length}/${os.length}`);
const ce=group(clean).filter(s=>has(s,"client_error"));
console.log(`client_error 세션 ${ce.length}, 직전`, count(ce.map(s=>s[s.findIndex(e=>e.name==="client_error")-1]?.name),x=>x));
```
