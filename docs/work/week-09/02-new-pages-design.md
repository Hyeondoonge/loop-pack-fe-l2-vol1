## 0. 화면 내용을 정한 기준

과제 문서(`docs/assignments/week-09.md`)는 화면 구성을 지정하지 않는다. 화면을 만들라는 문장은 121번 줄 하나이고 "보호할 화면이 아직 없으면 **만들어야 검증할 수 있어요**"로 존재만 요구한다. 체크리스트(320번 줄)도 "만들었는가"만 묻는다. 오히려 143·192번 줄은 "없는 화면은 빼고 뺐다는 사실을 적으라"고 한다.

**그래서 화면 내용은 과제의 요구가 아니라 판단이고, 기준을 둘로 좁힌다.**

1. 로그아웃·세션 만료를 처리할 수 있는 기능
2. 실재하는 API의 응답 데이터를 보여줄 수 있는 화면

두 기준 중 어디에도 걸리지 않는 요소는 만들지 않는다. 각 화면의 "만들지 않는 것" 표가 그 결과다.

### 레퍼런스: 무신사

요소 배치와 정보 위계를 무신사에서 가져온다.

- 이 프로젝트의 상품 데이터가 이미 무신사 형식이다 — `[11월 20일 예약배송] Winter Rocky Pants 2color 윈터 로키팬츠 OG`처럼 대괄호 프로모션 접두사 + 영문/한글 병기 + 색상 수 표기.
- 01번 문서에서 복원 파라미터 방식의 근거로 이미 무신사를 인용했다. 레퍼런스를 하나로 유지하면 판단 기준이 갈리지 않는다.
- 시각 언어가 현 테마와 같은 계열이다 — 흑백 기반, 라운드 거의 없음, 얇은 회색 선으로 구획.

### 범위 원칙 — 백엔드가 없는 UI는 만들지 않는다

무신사 주문서에는 배송지·배송 메모·쿠폰·적립금·결제수단·약관 동의가 있다. 이 프로젝트의 API에는 하나도 없다.

| API | 주는 것 |
| --- | --- |
| `GET /api/auth/me` | `id` · `name` · `email` 뿐. 등급·마일리지·쿠폰 없음 |
| `POST /api/orders` | 받는 본문이 `{ items: [{ productId, quantity }] }` 뿐. 배송지도 결제수단도 안 받음 |
| `GET /api/orders` | `{ id, createdAt, items }` 뿐. **금액도 배송 상태도 없음** |
| `GET /api/products` | 상품의 이름·브랜드·가격·이미지 |

없는 데이터를 화면에 그리면 전부 가짜 값이 된다. 그러면 5단계에서 "인증 구현 한 곳을 망가뜨려 E2E가 잡는지 본다"는 실험 대상이 가짜 UI에 묻힌다.

## 1. 페이지 정의

| 경로 | 화면 | 보호 | 화면이 하는 일 | 내용의 출처 |
| --- | --- | --- | --- | --- |
| `/mypage` | 마이페이지 | **보호** | 로그인한 계정 확인, 로그아웃 | `GET /api/auth/me` |
| `/orders` | 주문 내역 | **보호** | 내가 한 주문을 확인 | `GET /api/orders` + `GET /api/products` |
| `/orders/new` | 주문서 | **보호** | 확정된 품목으로 주문 전송 | 장바구니 + `GET /api/products` → `POST /api/orders` |
| `/cart` | 장바구니 | 비보호 | 담은 상품의 **수량을 정하고 금액을 확인** | 장바구니 + `GET /api/products` |
| `/wishlist` | 위시리스트 | 비보호 | 찜한 상품을 다시 봄 | 위시리스트 + `GET /api/products` |
| `/login` | 로그인 | 비보호 | 로그인, **세션 만료 안내** | `POST /api/auth/login` |

보호 경계는 01번 문서 4번 결정 — 계정이 있어야 성립하는 기능만 보호한다. 장바구니·위시리스트는 계정 없이도 성립한다.

### 화면이 나뉘는 기준 — 어디서 무엇을 정하는가

주문 흐름에서 상품과 수량이 확정되는 지점을 하나로 못박는다.

| 화면 | 상품 | 수량 |
| --- | --- | --- |
| 상품 목록 · 위시리스트 | 고르는 중 | 없음 |
| **장바구니** | 확정 (빼기 가능) | **여기서 정한다** |
| 주문서 | 확정 | **읽기 전용** |
| 주문 내역 | 확정 | 읽기 전용 |

주문서에서 수량을 바꿀 수 있으면 바꿀 때마다 할인 적용·무료배송 기준·재고를 다시 확인해야 한다. 지금은 쿠폰도 배송비도 없어 그 비용이 드러나지 않지만, 구조를 통상과 다르게 잡아두면 **그것들이 생기는 순간 주문서가 장바구니의 일을 겸하게 된다.**

## 2. 공통 스타일 규칙

기존 테마(`globals.css` · `commerce.css`)를 그대로 잇는다. 새 색도 새 폰트도 도입하지 않는다.

| 항목 | 값 |
| --- | --- |
| 배경 / 글자 | `#ffffff` / `#171717` |
| 폰트 | `Arial, Helvetica, sans-serif` |
| 테두리 | `1px solid #c8c8c8` — **라운드 0** (프로젝트 전체에 `border-radius` 없음) |
| 플레이스홀더 · 이미지 자리 | `#ececec` |
| 주 버튼 | 배경 `#000` / 글자 `#fff` / `font-weight: 600` / `min-height: 44px` |
| 보조 버튼 | 테두리만 (`1px solid #c8c8c8`, 배경 투명) |
| 비활성 버튼 | 배경·테두리 `#c8c8c8` / 글자 `#666` |
| 보조 텍스트 | `#666` |
| 포커스 링 | `outline: 3px solid #2557a7; outline-offset: 3px` |
| 본문 폭 | `min(100% - 32px, 1200px)`, 가운데 정렬 |
| 섹션 간격 | 위 여백 `40px`, 제목 아래 `16px` |
| 오류 문구 | `role="alert"` + 검정 + 굵게 — **색으로 구분하지 않는다** |

마지막 항목이 중요하다. 이미 오류를 빨강이 아니라 굵기로 알리고 있어 색각 이상 사용자에게도 전달된다. 새 화면도 이 규칙을 잇는다.

### 상품 줄 (주문 내역 · 주문서 · 장바구니 공통)

세 화면이 같은 줄 모양을 쓴다. 금액이 한 열에 세로로 정렬돼야 눈으로 더할 수 있다.

```
┌────────────────────────────────────────────────────────┐
│ ┌────┐  상품명                                          │
│ │img │  단가 · 수량                        소계         │
│ └────┘                                                  │
└────────────────────────────────────────────────────────┘
```

- 썸네일 80×80 정사각형 고정, 자리색 `#ececec` — 이미지가 늦게 와도 줄이 밀리지 않는다.
- 줄 사이 얇은 구분선. 목록 전체는 `1px solid #c8c8c8` 테두리로 감싼다.
- 소계는 오른쪽 정렬, 굵게. 480px 이하에서 소계가 다음 줄 전체 폭으로 내려가 오른쪽 정렬을 유지한다.

### 합계 줄

```
┌────────────────────────────────────────────────────────┐
│  상품 5개                                   510,000원   │
└────────────────────────────────────────────────────────┘
```

테두리 상자, 좌우 양끝 정렬. 숫자 자릿수가 바뀌어도 아래 버튼이 움직이지 않도록 높이를 미리 잡는다.

## 3. 마이페이지 `/mypage`

```
┌─ page-container ──────────────────────────────────────┐
│  마이페이지                                    (h1)     │
│  ┌────────────────────────────────────────────────┐   │
│  │  루퍼1 님                                       │   │
│  │  looper1@loopers.dev                            │   │
│  └────────────────────────────────────────────────┘   │
│                                                        │
│  주문 내역 보러 가기                                    │
│                                                        │
│  ┌────────────────────────────────────────────────┐   │
│  │                   로그아웃                      │   │
│  └────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────┘
```

계정 정보 상자와 로그아웃 버튼은 본문 폭 전체. 로그아웃은 **보조 버튼**으로 둔다 — 화면당 주 버튼은 하나인데, 이 화면에는 주 버튼으로 삼을 행동이 없다.

### 기능 요구사항

| # | 요구사항 | 인증 | 남긴 기준 |
| --- | --- | --- | --- |
| M1 | 로그인한 계정의 이름·이메일을 보여준다 | **필수** | 기준 2 |
| M2 | 주문 내역으로 이동할 수 있다 | — | 진입 경로 (헤더에 주문 내역 링크가 없다) |
| M3 | 로그아웃할 수 있고, 끝나면 홈으로 간다 | **필수** | 기준 1 |
| M4 | 로그아웃해도 장바구니·위시리스트는 남는다 | — | 01번 3번 결정 |

- **M1이 이 화면을 보호 경로로 만드는 근거다.** 01번 문서의 "표시할 정보가 로그인 없이는 존재하지 않는다"가 이 항목을 가리킨다.
- **M3의 이동처가 홈인 이유**: 마이페이지는 보호 경로라 로그아웃한 사용자가 머물 수 없다. 남으면 가드가 다시 로그인으로 보내는데, 그건 "세션이 만료돼 튕긴 것"과 화면상 구분되지 않는다. 의도한 로그아웃을 만료처럼 보이게 하면 안 된다.
- **M4는 눈으로 확인되는 지점이다.** 로그아웃 직후 홈에서 헤더의 장바구니·위시리스트 개수가 그대로 보이는 것이 정상 동작이고, 이게 01번 3번 결정의 검증 자리가 된다.

### 접근성

- 이메일은 `mailto:` 링크로 만들지 않는다. 계정 식별용 표시지 연락 수단이 아니다.
- 링크 이름에 목적지를 넣는다 — "보러 가기"만으로는 링크만 훑을 때 어디로 가는지 알 수 없다.
- 계정 정보 영역의 제목은 화면에 보이지 않게 두되 마크업에는 남긴다. 제목 없이 상자만 있으면 제목 단위 탐색에서 이 영역이 사라진다.

### 만들지 않는 것

| 뺀 것 | 이유 |
| --- | --- |
| 활동 요약(주문 건수·장바구니·위시리스트 카드) | 장바구니·위시리스트 개수는 API 값이 아니라 기준 2에 안 걸린다. 주문 건수는 API 값이지만 주문 내역 화면이 같은 응답을 이미 온전히 보여줘 중복 |
| 회원 등급·마일리지·쿠폰 | `GET /api/auth/me` 응답에 없다. 그리면 전부 가짜 값 |
| 프로필 수정 | 수정 API가 없다 |
| 주문 상태별 요약(배송중/배송완료) | 주문 데이터에 상태가 없다 |

## 4. 주문 내역 `/orders`

무신사 주문/배송 조회의 카드 구조. 주문 하나가 카드 하나고, 머리에 주문일시·주문번호, 몸통에 상품 줄, 발에 합계.

```
┌─ page-container ──────────────────────────────────────┐
│  주문 내역                                     (h1)     │
│  ┌────────────────────────────────────────────────┐   │
│  │  2026년 9월 2일 · 주문번호 o3            (h2)   │   │
│  ├────────────────────────────────────────────────┤   │
│  │ ┌────┐ [11월 20일 예약배송] Winter Rocky Pants  │   │
│  │ │img │ 79,000원 · 2개                158,000원 │   │
│  │ └────┘                                          │   │
│  │ ──────────────────────────────────────────────  │   │
│  │ ┌────┐ [Exclusive] Holiday Signature Ball Cap   │   │
│  │ │img │ 39,000원 · 1개                 39,000원 │   │
│  │ └────┘                                          │   │
│  ├────────────────────────────────────────────────┤   │
│  │  상품 3개                          197,000원   │   │
│  └────────────────────────────────────────────────┘   │
│  ┌── 이전 주문 ─────────────────────────────────┐     │
└────────────────────────────────────────────────────────┘
```

빈 상태: "아직 주문한 상품이 없습니다." + `상품 보러 가기`

### 기능 요구사항

| # | 요구사항 | 인증 |
| --- | --- | --- |
| H1 | 로그인한 계정의 주문만 보여준다 | **필수** |
| H2 | 최신 주문이 위로 온다 | — |
| H3 | 주문마다 주문일시와 주문번호를 보여준다 | — |
| H4 | 항목마다 상품명·이미지·단가·수량·소계를 보여준다 | — |
| H5 | 주문 합계와 총 수량을 보여준다 | — |
| H6 | 주문이 없으면 안내와 상품 목록 링크를 보여준다 | — |

- **H1이 이 화면의 보호 근거다.** 서버가 로그인한 계정으로 필터링해 조회하므로 계정 없이 성립할 수 없다.
- **H2를 화면에서 뒤집는다.** 서버가 정렬을 보장하지 않고 새 주문을 뒤에 붙이기만 한다. 최근 주문을 먼저 보는 것이 주문 내역의 기본 기대다.
- **H4에는 조인이 필요하다.** 주문 API가 상품 id와 수량만 주므로 이름·가격·이미지는 상품 API에서 붙인다. 그대로 그리면 화면에 "p1 × 2"가 뜬다.

### 상품 정보를 못 찾은 항목의 표시 규칙

지금 데이터에서는 일어나지 않지만(주문 API가 받는 상품 id 범위와 카탈로그가 정확히 같다), 규칙이 없으면 상품 API가 일부 실패했을 때 금액 자리에 **`NaN원`**이 뜬다. 금액 화면에서 가장 나쁜 실패 모습이다.

- 상품명 자리에는 상품 id를, 금액 자리에는 금액 대신 **"상품 정보 없음"**을 보여준다.
- 그 항목은 합계에서 **제외**하고, 합계 옆에 일부가 빠졌음을 밝힌다. 틀린 합계를 맞는 것처럼 보여주지 않는다.

### 접근성

- 주문 목록은 목록 구조로 두고, 주문 카드 제목에 **주문번호를 포함**한다. 제목 단위로 훑을 때 주문이 구분된다.
- 주문일시는 화면에 한국어 형식으로, 기계에는 ISO 값으로 함께 전달한다.
- 썸네일 대체 텍스트는 상품명 전체. 상품 카드가 이미 쓰는 규칙을 잇는다.
- 한 줄에 "79,000원 · 2개 · 158,000원" 세 숫자가 나란히 놓인다. 시각적으론 위치로 구분되지만 음성으로는 숫자 셋이 연달아 읽힌다. 각 값 앞에 **보이지 않는 라벨**(단가/수량/소계)을 둬 의미를 붙인다.
- 날짜와 주문번호 사이의 가운뎃점은 읽히지 않게 감추고, 대신 끊어 읽을 쉼표를 둔다.
- 금액 표기 형식은 화면마다 갈리지 않게 프로젝트 공용 형식을 쓴다.

### 만들지 않는 것

| 뺀 것 | 이유 |
| --- | --- |
| 주문 상세 페이지 | 단건 조회 엔드포인트가 없다. 목록 카드에 이미 전체 항목이 들어간다 |
| 기간·상태 필터 | 정렬 기준이 주문일시 하나뿐이고 주문 수가 적다 |
| 배송 상태 배지·배송 조회 | 주문 데이터에 상태가 없다 |
| 주문 취소·반품·재주문 | 해당 엔드포인트가 없다 |
| 페이지네이션 | 서버가 전체를 한 번에 준다. 페이지 파라미터가 없다 |

## 5. 주문서 `/orders/new`

무신사 주문서에서 배송지·메모·쿠폰·적립금·결제수단·약관을 **전부 뺀** 형태. 남는 건 주문 상품, 결제 금액, 주문 버튼 셋이다.

```
┌─ page-container ──────────────────────────────────────┐
│  주문서                                        (h1)     │
│  주문 상품                                     (h2)     │
│  ┌────────────────────────────────────────────────┐   │
│  │ ┌────┐ [11월 20일 예약배송] Winter Rocky Pants  │   │
│  │ │img │ 79,000원 · 2개                158,000원 │   │
│  │ └────┘                                          │   │
│  │ ──────────────────────────────────────────────  │   │
│  │ ┌────┐ [Exclusive] Holiday Signature Ball Cap   │   │
│  │ │img │ 39,000원 · 1개                 39,000원 │   │
│  │ └────┘                                          │   │
│  └────────────────────────────────────────────────┘   │
│  수량을 바꾸려면 장바구니에서 수정해 주세요.              │
│                                                        │
│  ┌────────────────────────────────────────────────┐   │
│  │  총 결제 금액                      197,000원   │   │
│  └────────────────────────────────────────────────┘   │
│  ┌────────────────────────────────────────────────┐   │
│  │           197,000원 주문하기                    │   │
│  └────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────┘
```

빈 장바구니: "주문할 상품이 없습니다." + `상품 보러 가기`

- 주문 버튼은 주 버튼. 총 결제 금액 상자를 그 바로 위에 둔다 — 무신사도 결제 버튼 직전에 최종 금액을 다시 보여준다.
- 상품 줄은 주문 내역과 **완전히 같은 모양**이다. 두 화면이 보여줄 것이 같기 때문이다.

### 기능 요구사항

| # | 요구사항 | 인증 |
| --- | --- | --- |
| N1 | 장바구니에 담긴 상품과 수량을 **읽기 전용**으로 보여준다 | — |
| N2 | 수량을 바꾸려면 장바구니로 가라고 안내한다 | — |
| N3 | 항목별 소계와 총 결제 금액을 보여준다 | — |
| N4 | 주문을 전송한다 | **필수** |
| N5 | 성공하면 주문 내역으로 이동하고, 주문된 상품이 장바구니에서 빠진다 | — |
| N6 | 장바구니가 비어 있으면 안내 화면을 보여준다 | — |
| N7 | 전송에 실패하면 이유를 알려주고, 장바구니는 그대로 둔다 | — |

- **N5에 주문 완료 화면을 따로 만들지 않는다.** 방금 만든 주문이 주문 내역 맨 위에 나타나 완료 확인이 그 자리에서 된다. 화면을 하나 덜 만들고, 4단계 E2E의 단언이 화면 문구가 아니라 데이터에 걸려 5단계에서 문구를 바꿔도 깨지지 않는다.
- **N5에서 장바구니를 비우는 기준은 "주문에 담겨 나간 항목"이다.** 지금은 장바구니 전체를 주문하므로 결과가 전체 비움과 같지만, 기준을 이렇게 두면 나중에 일부만 주문하게 되어도 규칙이 그대로 맞는다.
- **N7이 중요하다.** 실패했는데 장바구니를 비우면 사용자가 담아둔 것을 잃고 되돌릴 방법이 없다.
- **N6의 빈 상태는 예외가 아니라 자주 지나가는 정상 경로다.** 장바구니가 새로고침·가드 리다이렉트로 비워지기 때문이다(9장). 안내 문구와 상품 목록 링크를 갖춘 화면으로 다룬다.

### 접근성

- 주문 버튼 라벨에 금액을 넣는다("197,000원 주문하기"). 버튼만 읽어도 얼마를 결제하는지 알 수 있어 금액 상자까지 되짚어 올라가지 않아도 된다.
- 전송 중에는 버튼을 비활성으로 둔다. 중복 주문을 막는 동시에 진행 중임이 보인다.
- 실패 문구는 주문 버튼 근처에 `role="alert"`로 둔다.
- 금액 자리와 실패 문구 자리에 높이를 미리 잡는다. 오류가 나타날 때 주문 버튼이 움직이면 잘못 누르게 된다.

### 만들지 않는 것

| 뺀 것 | 이유 |
| --- | --- |
| 수량 변경 | 장바구니가 그 자리다(1장) |
| 항목 삭제 | 무신사 주문서에도 없다. 두면 "주문서에서 뺀 게 장바구니에도 반영되나?"라는 답할 필요 없는 질문이 생긴다 |
| 배송지 선택·배송 메모 | 주문 API 본문이 상품과 수량만 받는다 |
| 쿠폰·적립금·결제수단 | 데이터도 엔드포인트도 없다 |
| 약관 동의 체크박스 | 서버가 받지 않는다. 주문 버튼만 막는 장식이 된다 |
| 배송비 줄 | 무료배송 여부는 있지만 **배송비 금액이 없다.** 지어내면 총액이 거짓이 된다 |
| 상품금액/할인/최종금액 3단 표기 | 할인이 없어 세 줄이 모두 같은 값이 된다. **금액 줄 하나만 둔다** |

### 계측 연결점 (2단계에서 씀)

과제 143번 줄이 **주문 시작 · 주문 완료** 계측을 요구한다. 이 화면이 두 지점을 모두 갖는다.

- **주문 시작** — 주문서 화면에 들어온 시점. 주문 버튼 클릭은 이미 성공/실패로 갈리므로 "시작"이 될 수 없다.
- **주문 완료** — 주문이 성공한 시점. 화면 이동 전이다.

## 6. 장바구니 `/cart`

주문 흐름에서 **수량과 금액을 정하는 유일한 화면**이다. 상품은 이미 골랐으므로 탐색용 카드 그리드가 아니라 계산용 세로 목록으로 둔다.

```
┌─ page-container ──────────────────────────────────────┐
│  장바구니                                      (h1)     │
│  ┌────────────────────────────────────────────────┐   │
│  │ ┌────┐ FRAME CASE Air Bumper                   │   │
│  │ │img │ 25,000원 · [ 4 ]개    100,000원  [삭제] │   │
│  │ └────┘                                          │   │
│  │ ──────────────────────────────────────────────  │   │
│  │ ┌────┐ [FW23]아톰 후디 남성(6colors)            │   │
│  │ │img │ 410,000원 · [ 1 ]개   410,000원  [삭제] │   │
│  │ └────┘                                          │   │
│  └────────────────────────────────────────────────┘   │
│  ┌────────────────────────────────────────────────┐   │
│  │  상품 5개                          510,000원   │   │
│  └────────────────────────────────────────────────┘   │
│  ┌────────────────────────────────────────────────┐   │
│  │                   주문하기                      │   │
│  └────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────┘
```

빈 상태: "담은 상품이 없습니다." + `상품 보러 가기`

주문 내역·주문서와 **같은 줄 모양**을 쓴다. 다른 것은 수량 자리에 입력칸이 들어가고 오른쪽 열에 삭제가 붙는다는 점뿐이다. 소계와 삭제는 오른쪽 열에 세로로 쌓는다.

### 기능 요구사항

| # | 요구사항 |
| --- | --- |
| C1 | 담은 상품의 이미지·이름·단가를 보여준다 |
| C2 | 항목마다 수량을 바꿀 수 있다 |
| C3 | 항목을 뺄 수 있다 |
| C4 | 항목별 소계와 총 수량·합계를 보여주고, 수량을 바꾸면 즉시 반영한다 |
| C5 | 주문서로 이동할 수 있다 |
| C6 | 1 미만이거나 정수가 아닌 수량은 받지 않는다 |

- **C6의 기준은 서버가 주문을 400으로 막는 조건과 같다.** 화면과 서버의 검증 기준이 갈리면, 화면에서는 통과했는데 주문에서 실패하는 상황이 생긴다.
- **C5가 4단계 필수 E2E 시나리오의 실제 경로다.** 미로그인 상태로 주문하기를 누르면 로그인으로 갔다가 주문서로 돌아온다 — URL을 직접 치지 않고도 "미로그인으로 보호 경로 진입 → 로그인 → 원래 경로 복원"이 재현된다.

### 접근성

- 수량 입력의 이름에 **상품명을 포함**한다. 화면에는 "개"만 붙어 있어 폼 컨트롤만 훑는 사용자에게는 입력칸 여러 개가 구분되지 않는다.
- 삭제 버튼도 `{상품명} 장바구니에서 빼기`로 둔다. "삭제"만 있으면 무엇을 지우는지 알 수 없다.
- 합계 변화를 음성으로 알린다(`aria-live="polite"`). 수량을 바꾸면 화면 다른 곳의 숫자가 바뀌는데 그 변화가 알려지지 않으면 조작 결과를 알 수 없다. 입력 도중 끼어들지 않도록 `polite`.
- 수량 증감 버튼을 따로 만들지 않는다. 브라우저 기본 숫자 입력이 그 역할을 하고 키보드 위/아래 화살표도 그대로 동작한다.
- 수량 입력은 문장 안에 놓이지만 **터치 목표 44px은 줄이지 않는다.**

### 만들지 않는 것

| 뺀 것 | 이유 |
| --- | --- |
| 전체 선택 체크박스·부분 주문 | 주문서가 장바구니 전체를 대상으로 한다. 선택 상태를 둘 자리가 없다 |
| 담은 개수 문구 | 목록이 곧 개수다. 헤더에도 이미 개수가 있다 |
| 재고·품절 표시 | 주문 시 검증은 서버 몫이다. 화면에 재고를 그리면 서버 판정과 어긋날 수 있다 |
| 찜으로 옮기기 | 위시리스트 API가 없다(클라이언트 상태). 옮겨도 남는 곳이 없다 |

## 7. 위시리스트 `/wishlist`

아직 고르는 중인 화면이다. 사진을 견주어 보는 자리라 **상품 목록·홈과 같은 카드 그리드**를 쓴다. 수량도 금액 합계도 없다.

```
┌─ page-container ──────────────────────────────────────┐
│  위시리스트                                    (h1)     │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐        │
│  │[img] │ │[img] │ │[img] │ │[img] │ │[img] │        │
│  │브랜드 │ │브랜드 │ │      │ │      │ │      │        │
│  │상품명 │ │상품명 │ │      │ │      │ │      │        │
│  │가격   │ │가격   │ │      │ │      │ │      │        │
│  │[찜][담기]│[찜][담기]│      │ │      │ │      │        │
│  └──────┘ └──────┘ └──────┘ └──────┘ └──────┘        │
```

빈 상태: "찜한 상품이 없습니다." + `상품 보러 가기`

### 기능 요구사항

| # | 요구사항 |
| --- | --- |
| W1 | 찜한 상품을 상품 목록과 같은 카드로 보여준다 |
| W2 | 카드의 찜 버튼으로 그 자리에서 뺄 수 있다 |
| W3 | 카드의 담기 버튼으로 장바구니에 담을 수 있다 |

- **W2에 전용 삭제 버튼을 만들지 않는다.** 카드의 찜 버튼이 이미 토글이고, 이 화면의 상품은 모두 눌린 상태다. 삭제를 따로 두면 같은 일을 하는 컨트롤이 카드 하나에 둘이 된다.
- 그리드 열 수와 중단점은 상품 목록과 같다(5열 → 960px 3열 → 720px 2열).

### 만들지 않는 것

| 뺀 것 | 이유 |
| --- | --- |
| 수량·금액 합계 | 찜에는 수량 개념이 없고 결제 대상도 아니다 |
| 전체 담기 | 한 번에 담을 이유가 약하고, 담기 버튼이 카드마다 이미 있다 |
| 정렬·필터 | 찜 개수가 적고 정렬 기준이 없다(담은 순서뿐) |

## 8. 로그인 `/login` — 세션 만료 안내

과제 완료조건 131번 줄은 "세션이 만료되면 **다음에 무엇을 해야 할지 화면에서** 알 수 있어요"를 요구한다.

01번 문서 1번 결정에 따라 만료된 보호 화면은 그 자리에 머물지 않고 로그인 화면으로 보낸다. **따라서 만료 안내가 보이는 화면은 보호 화면이 아니라 로그인 화면이다.**

```
┌─ page-container ──────────────────────────────────────┐
│                     로그인               (h1)          │
│         ┌──────────────────────────────────┐          │
│         │  로그인 세션이 만료되었습니다.      │ ← 만료로 왔을 때만
│         │  다시 로그인하면 보던 화면으로       │          │
│         │  돌아갑니다.                       │          │
│         └──────────────────────────────────┘          │
│         ┌──────────────────────────────────┐          │
│         │  이메일    [                  ]   │          │
│         │  비밀번호  [                  ]   │          │
│         │            [ 로그인 ]              │          │
│         └──────────────────────────────────┘          │
└────────────────────────────────────────────────────────┘
```

| # | 요구사항 |
| --- | --- |
| L1 | 만료로 왔을 때만 안내를 보여준다. 평범한 로그인·미로그인 가드에는 보이지 않는다 |
| L2 | 안내는 폼 **위**에 둔다 |
| L3 | 안내 문구가 두 가지를 말한다 — 무슨 일이 있었는지(만료), 다음에 무엇이 일어나는지(원래 화면 복귀) |

- **L2의 이유**: 폼을 지나 아래에 있으면 이유를 모른 채 입력을 시작하게 된다.
- **L3의 두 번째가 완료조건이 요구하는 것이다.**
- 안내의 역할은 `role="status"`다. `alert`이 아닌 이유는 사용자 조작에 대한 오류가 아니라 화면 진입 시점의 상태 안내이기 때문이다. 자격 증명 실패(`role="alert"`)와 역할이 갈려야 두 상황이 섞이지 않는다.
- **L1이 필요한 이유**: 01번 2번 결정대로 미로그인과 만료는 다른 문구를 받아야 한다. 미로그인 사용자에게 "만료되었습니다"는 틀린 다음 행동을 알려준다.

## 9. 진입 동선

화면을 만들어도 갈 길이 없으면 4단계 E2E가 URL을 직접 여는 방식이 된다. 실제 사용자 경로를 만든다.

| 자리 | 링크 | 목적 |
| --- | --- | --- |
| 헤더 `위시리스트 N` | → `/wishlist` | 위시리스트 진입점 |
| 헤더 `장바구니 N` | → `/cart` | 장바구니 진입점 |
| 헤더 `{이름}님` | → `/mypage` | 마이페이지 진입점 |
| 장바구니 `주문하기` | → `/orders/new` | **비보호 → 보호 경로로 넘어가는 실제 경로** |
| 마이페이지 `주문 내역 보러 가기` | → `/orders` | 주문 내역 진입점 |

- **헤더 개수는 총 수량이 아니라 품목 수다.** 수량을 올려도 헤더 숫자는 그대로다 — 커머스 헤더의 통상 표기다.
- 로그아웃은 헤더에 두지 않는다(10-2).

### 알려진 화면 동작 — 장바구니는 전체 새로고침에서 비워진다

장바구니·위시리스트는 브라우저 메모리에만 있다. 새로고침, 그리고 미로그인 가드나 세션 만료로 인한 화면 전환은 문서를 다시 받으므로 **담긴 것이 사라진다.**

결과: 미로그인으로 주문서에 들어가려다 로그인한 뒤 주문서로 돌아오면 **장바구니가 비어 있다.** 경로 복원 자체는 성공하지만 주문할 상품이 없다.

**이 동작을 그대로 둔다.** 근거와 대안 비교는 [03-implementation-notes.md](./03-implementation-notes.md). 화면 관점에서는 빈 주문서가 이미 설계된 정상 상태(N6)라 깨지지 않고 안내 화면으로 떨어진다.

## 10. 화면 차원의 판단 기록

### 10-1. ⚠️ 판단 필요 — 찜 / 위시리스트 이름이 갈려 있다

한 개념에 세 이름이 붙어 있다.

| 자리 | 표기 |
| --- | --- |
| 상품 카드 버튼에 보이는 글자 | **찜** |
| 그 버튼을 음성이 읽는 이름 | **위시리스트** |
| 헤더·페이지 제목 | **위시리스트** |
| 페이지 본문 문구 | **찜**한 상품 |
| 01번 문서 4번 결정 표 | **찜 목록** |

장바구니도 같은 구조다 — 버튼은 **담기**, 나머지는 **장바구니**.

버튼 라벨(찜·담기)은 행동이고 화면 이름(위시리스트·장바구니)은 장소라, 다른 것이 자연스러운 자리도 있다. 문제는 **같은 자리에서 갈리는 경우**다. 버튼에 보이는 글자는 "찜"인데 음성이 읽는 이름은 "위시리스트"라, 화면을 보는 사람과 듣는 사람이 서로 다른 이름을 쓰게 된다.

지금은 **바꾸지 않았다.** 사용자 노출 문구 변경이고 E2E 셀렉터가 이 라벨에 의존한다. 이름을 고르면 셀렉터와 문구를 함께 옮겨야 한다.

### 10-2. 로그아웃 버튼을 헤더에도 둘 것인가 — 두지 않는다

- **계측 자리가 하나로 남는다.** 과제 144번 줄이 로그아웃 시점의 `reset()` 자리를 정하라고 요구한다. 진입점이 둘이면 계측도 둘이 되고, 한쪽을 빠뜨리면 그 경로로 나간 사용자의 로그만 이전 계정에 붙는다. 로그를 집계할 때까지 드러나지 않는 종류의 누락이다.
- 헤더의 `{이름}님`이 이미 마이페이지 링크다. 로그아웃까지 헤더에 두면 계정 관련 진입점이 헤더에 둘, 마이페이지에 하나로 흩어진다.

대가는 비보호 화면에서 로그아웃하려면 마이페이지를 한 번 거쳐야 한다는 것이다. 클릭 한 번이고 로그아웃은 자주 하는 행동이 아니라 감수한다.

### 10-3. 주문 내역과 주문서가 같은 줄 모양을 쓴다

주문서를 읽기 전용으로 정하면서 두 화면이 보여줄 것이 완전히 같아졌다. 두 화면의 줄 모양이 어긋나면 사용자는 "주문서에서 본 것과 주문 내역에 남은 것이 같은가"를 눈으로 대조하기 어려워진다. 같은 모양으로 못박는다.
