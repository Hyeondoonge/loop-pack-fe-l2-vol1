### 4-1. 관찰 지점을 옮긴 사례

#### `productListFilters.ts` mutation 결과

killed 6 / survived 4 (전체 10개). 살아남은 4개:

| 위치                            | 변형                                            | 비고                      |
| ------------------------------- | ----------------------------------------------- | ------------------------- |
| `:16` `serialize`               | `String(Math.round(value))` → `() => undefined` | 미검토(이번 문서 범위 밖) |
| `:20` `q` 기본값 `''`           | → `'Stryker was here!'`                         | 미검토(이번 문서 범위 밖) |
| `:21` `category` 기본값 `'all'` | → `''`                                          | 3절에서 등가로 확정       |
| `:22` `sort` 기본값 `'latest'`  | → `''`                                          | -                         |

`:16`, `:20`은 이번 검토(3절·4-1) 범위 밖이라 별도 판단이 필요하다 — 다룰지 여부는 후속 결정.

**보강 전**

- `productListFilters.ts:22`의 `sort` 기본값 `'latest'` 변형이 통합 테스트로도 안 잡힘
- 원인: `mocks`의 `toConditionKey`가 빠진 `sort` 파라미터를 `?? 'latest'`로 스스로 되메꿔, 실제로는
  파라미터가 안 실렸는데도 정상 응답과 같은 스텁을 돌려줌(직접 로그로 확인)
- 겉보기엔 `category`(3절)처럼 등가로 보였으나, 실제 시드 데이터로 직접 비교한 결과 프로덕션은
  등록 순으로 응답이 달라짐을 확인 — **등가가 아니라 mock이 만든 착시**
- 통합 테스트를 더 추가해도 같은 모킹을 거치는 한 계속 흡수돼 무의미함

**보강 후**

- 테스트 추가 대신 관찰 지점을 단위로 이동: `productListParsers.sort.defaultValue`를 직접 단언
- 통합 레벨에서 볼 수 없던 차이를 단위 레벨에서 직접 확인하는 방식으로 우회

## 5. 3단계 손 실험 대비 도구가 추가로 찾아준 것

3단계는 값이 갈리는 경계(페이지 수, 결과 0/1개, 로딩/갱신, 담김/안 담김, 페이지 번호)를 사람이
먼저 짚고 그 지점만 뒤집었다. Stryker는 경계를 짚지 않고 파일 전체의 연산자·리터럴·분기를
기계적으로 바꿔봤고, 그 결과 손 실험 설계 단계에서는 애초에 후보에 오르지 않았던 지점들이 나왔다.

- **정상 케이스 자체가 없던 지점**: `createIdSetStore.ts`의 add/remove, `getProductListData.ts`의
  `popular` 2차 정렬(리뷰 수 동률일 때 평점 내림차순)은 "경계"가 아니라 "그 기능을 다루는 테스트가
  하나도 없는" 경우였다. 3단계는 경계를 뒤집는 실험이라 애초에 이 지점을 겨냥하지 않았을 것이다.
- **같은 로직의 중복 실장**: `getHomeData.ts:8`이 `getProductListData.ts:30`과 같은 정렬 규칙을
  복붙해 갖고 있다는 사실은 변형이 두 파일에서 각각 살아남고서야 드러났다. 코드 리딩만으로는
  놓치기 쉬운 중복이었다.
- **모킹이 만든 착시**(4-1절): `productListFilters.ts:22`의 `sort` 기본값 변형은 통합 테스트를
  아무리 추가해도 잡히지 않았는데, 원인은 버그가 아니라 mock의 `toConditionKey`가 빠진 파라미터를
  스스로 되메워 실제 프로덕션 차이를 가려버린 것이었다. 3단계 실험은 결과 화면 기준으로 판정했기
  때문에 이 착시를 만날 일이 없었고, 단위 레벨로 관찰 지점을 옮기고 나서야 실체가 보였다.
- **의미 없는 죽은 코드**: `apiFetch.ts`의 `this.name = 'ApiError'`는 소비처가 프로젝트 어디에도
  없어 변형이 등가로 판정됐다. 동작을 확인하는 실험(3단계)으로는 발견될 이유가 없는, 코드 자체가
  불필요했던 사례다.
