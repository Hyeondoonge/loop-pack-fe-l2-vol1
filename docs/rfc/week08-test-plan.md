### 추가 순수로직 테스트 대상

#### 3.1 현재 페이지 보정

1. 계산이 잘못된 경우 UX 저하 (필터링이 잦은데 유저는 빈화면을 보며 탐색 경험이 끊김)
2. 경계값이 뚜렷해서 검증 가치가 높음

#### 3.2 목록 페이지 metadata 파생

1. 깨져도 페이지 자체는 문제없이 동작해서 알아차리기 어려움
2. 검색결과·공유 링크를 통해 들어오는 유입에 직접 영향
3. 조건 조합이 다양해 케이스별 확인 가치가 있음
4. 화면 렌더나 네트워크 없이 값만 비교하면 되므로 확인 비용이 낮음

## 2. 애매했던 판단

**1. 담기 → 헤더 개수 항목(1·12·15번)을 어디까지 합칠까**

- 선택지: A. 12번 하나로 셋 다 흡수 vs B. 1번만 흡수하고 15번은 재정의해 유지 vs C. 셋 다 그대로 유지
- 결정: B
- 근거:
  - C 제외: 1번과 12번은 "버튼 클릭 → 스토어 갱신 → Header 반영"으로 같은 메커니즘. 12번(추가+재클릭 복귀)이 범위가 더 넓어 1번을 부분집합으로 포함 → 완전 중복
  - A 제외: 흡수 근거였던 "Header의 레이아웃 고정 마운트"가 곧 15번의 검증 대상. 통합은 layout 조립도 라우터도 없어 원리적으로 못 봄
  - 15번이 12번과 겹친 원인은 층이 아니라 순서(담기가 이동 뒤). 홈에서 담기 → 이동 → 목록에서 담기로 뒤집으면 고유 assert는 "라우트를 넘겨도 유지·누적"

**2. 13번(뒤로·앞으로 가기)을 어느 층에 둘까**

- 선택지: A. E2E vs B. 통합
- 결정: B(통합)
- 근거:
  - A 제외: "히스토리 관리"라 E2E가 당연해 보이지만, E2E는 브라우저 기동·프로덕션 빌드까지 얹혀 구동 비용이 큼
  - 통합 가능: `nuqs/adapters/react`(운영과 같은 코드 경로)가 실제 `history.pushState`/`popstate` 사용 + jsdom이 whatwg-html 스펙대로 구현 → 운영과 같은 코드 경로가 jsdom에서 재현
  - 일반 원칙: 값싼 층 가능 여부를 먼저 확인, 불가가 확인된 뒤에만 비싼 층으로
