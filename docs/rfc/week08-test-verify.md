# week-08 3단계 — 내 테스트가 진짜 뭘 잡는지 확인해요

방법론(단위·통합·E2E)마다 구현을 일부러 망가뜨려 테스트가 잡는지 확인한 기록이다.
실험은 구현 코드 한 곳만 바꾸고, 테스트 코드는 건드리지 않았다.

이번 회차는 **경계값**만 노렸다. 값이 갈리는 지점(나누어떨어지지 않는 페이지 수, 결과 0개와 1개,
첫 페이지, 담김과 안 담김)을 한 칸씩 옮기거나 뒤집어, 그 경계를 지키는 단언이 실제로 있는지 확인했다.

## 실험별 상세

### 실험 1 (단위) — 전체 페이지 수를 셈하는 올림 · 단위는 살아남음

결과 개수를 페이지 크기로 나눠 전체 페이지 수를 낼 때 올림 대신 반올림을 쓰게 했다. 단위 81개는
전부 통과했고, 통합 4개가 대신 잡았다.

- 단위가 왜 못 잡았나: 이 함수의 단위 테스트 여섯 개가 전부 같은 조합(결과 30개, 페이지 크기 12)을
  쓴다. `30 ÷ 12 = 2.5`인데 소수부 0.5는 올림과 반올림이 **일치하는 유일한 값**이다. 빈 결과 케이스
  두 개는 나눗셈 앞에서 빠져나가 이 줄을 아예 지나지 않는다. 페이지 번호 쪽 경계(첫 페이지 / 마지막
  페이지 / 한 칸 초과 / 크게 초과)는 촘촘한데, 페이지 수를 **만들어내는** 축은 값이 하나뿐이었다.
- 실제로 무엇이 깨지나: 결과 개수가 페이지 크기의 절반보다 적으면(검색 결과 1~5개) 전체 페이지 수가
  0으로 계산된다. 첫 페이지에 있는데도 "범위를 넘겼다"고 판정되어 주소의 페이지를 0으로 되돌리려 든다.
- 통합이 잡은 것도 운에 가깝다: 통합 스텁이 마침 `14 ÷ 12 = 1.17`이라 반올림하면 1페이지가 되어
  2페이지 관련 테스트들이 무너졌다. 스텁 개수를 24개나 12개로 바꾸면 이 방어는 그대로 사라진다.
- 대응: 단위에 `마지막 조각도 한 페이지로 세어 전체 페이지 수를 낸다` 묶음을 추가했다. 나머지가
  절반보다 적은 조합(25·12), 한 페이지를 못 채우는 조합(5·12), 나누어떨어지는 조합(24·12)을 각각
  범위 안·범위 밖 두 방향으로 단언한다. 같은 변형을 다시 걸면 이제 **단위 2개가 먼저 잡는다.**

### 실험 2 (단위) — 문서 제목의 페이지 표기 경계 · 잡힘

"두 번째 페이지부터 제목에 페이지 번호를 붙인다"는 규칙의 경계를 한 칸 넓혀 첫 페이지에도 붙게 했다.
검색 엔진에 첫 페이지와 페이지가 표기된 제목이 중복으로 노출되는, 실제로 문제가 되는 변경이다.

- 실패 메시지로 원인을 알 수 있었나: **알 수 있었다.**
  `AssertionError: expected '상품 목록 (1페이지)' to be '상품 목록'` — 기대와 실제가 문자열 그대로
  나와서 "첫 페이지인데 페이지 표기가 붙었다"가 한 줄로 읽힌다. 테스트 이름
  `첫 페이지에는 페이지 표기를 붙이지 않는다`가 규칙까지 알려준다.

### 실험 3 (통합) — 결과 0개와 1개의 경계 · 살아남음

결과가 한 개일 때도 "검색 결과가 없습니다"가 뜨게 했는데 통합 21개가 전부 통과했다. 검색 결과가
한 개인 건 흔한 상황이라, 있는 상품을 없다고 말하는 사용자 영향이 큰 변경이다.

- 왜 못 잡았나: 빈 결과 테스트가 **0개**만 쓰고, 목록이 보이는 테스트는 12개·2개처럼 여유 있는 개수만
  쓴다. 경계 바로 옆인 **1개짜리 결과** 픽스처가 없어서 0과 1을 가르는 단언이 어디에도 없다.
- 대응: 상품 한 개짜리 응답 픽스처(`PRODUCT_LIST_STUBS.single`)를 만들고 통합에
  `결과가 하나뿐이면 안내 문구가 아니라 상품 카드 한 장을 보여준다`를 추가했다. 안내 문구가 없는지와
  카드가 정확히 한 장인지를 함께 본다. 같은 변형을 다시 걸면 **이 테스트가 잡는다.**

### 실험 4 (통합) — 첫 로딩과 갱신의 경계 · 살아남음

필터를 바꿔 다시 불러오는 동안에도 보고 있던 목록을 지우고 스켈레톤으로 덮게 했는데 전부 통과했다.
이전 결과를 유지한 채 갱신한다는 동작(화면이 깜빡이지 않게 하려고 일부러 넣은 것)이 통째로 사라져도
아무도 모른다는 뜻이다.

- 왜 못 잡았나: 필터를 바꾸는 테스트들이 전부 **최종 상태**만 본다(`findBy`로 새 목록이 나타나기를
  기다린다). 갱신이 진행되는 **중간 순간에 이전 목록이 남아 있는지**를 확인하는 단언이 없다.
- 대응: 통합에 `필터를 바꿔 다시 불러오는 동안에는 이전 조건의 목록이 화면에 남는다`를 추가했다.
  응답을 200ms 지연시킨 뒤 카테고리를 바꾸고, 새 결과가 오기 전 순간에 이전 조건의 상품이 그대로
  보이면서 결과 영역만 갱신 중으로 표시되는지 동기로 확인한다. 같은 변형을 다시 걸면 **이 테스트가 잡는다.**

### 실험 5 (E2E) — 담김 상태 표시의 경계 · 잡힘

담긴 상품과 안 담긴 상품의 표시를 뒤집었다. 단위·통합 102개는 전부 통과하고 E2E 하나만 실패했다.
통합 테스트는 버튼을 이름으로만 찾고 담김 표시를 읽지 않아서, 이 경계는 E2E에만 걸려 있다.

- 실패 메시지로 원인을 알 수 있었나: **알기 어려웠다.** 메시지가
  `locator.click: Test timeout of 30000ms exceeded — waiting for locator('button[aria-label$="장바구니"][aria-pressed="false"]')`라서
  "안 담긴 버튼을 못 찾았다"까지만 알려준다. 표시가 뒤집혔는지, 버튼이 아예 안 그려졌는지, 페이지가
  안 떴는지 구분되지 않는다. 게다가 30초를 기다린 뒤에야 실패한다.
- 대응: 통합에 `담기 전에는 담기지 않은 상태로, 담은 뒤에는 담긴 상태로 표시된다`를 추가했다.
  같은 변형을 다시 걸면 E2E가 30초를 기다리기 전에 **통합이 43ms 만에**
  `expected element to have attribute aria-pressed="false"`로 잡는다. E2E는 그대로 두었다 —
  라우트를 넘나드는 시나리오가 이 항목의 본래 목적이고, 표시 회귀의 1차 방어선만 통합으로 내렸다.

### 실험 6 (E2E) — 주소에 적히는 페이지 번호 · 잡힘

주소에 적히는 페이지 번호만 하나 작게 썼다. 화면은 2페이지인데 주소는 1페이지라, 새로고침하거나
링크를 공유하면 다른 페이지가 열린다.

- 실패 메시지로 원인을 알 수 있었나: **통합 쪽은 알 수 있었다.**
  `AssertionError: expected '1' to be '2'`가 테스트 이름 `페이지를 넘길 때는 page만 바뀌고 기존 조건이
유지된다`와 함께 나와서 주소에 적힌 페이지 값이 틀렸다는 게 바로 읽힌다. E2E 쪽은 새로고침 전후
  상태 객체 전체를 비교하는 방식이라 어디가 달라졌는지 찾는 데 한 단계가 더 걸린다.
- 계층에 대한 기록: E2E 항목(새로고침해도 같은 페이지)을 노린 변형인데 **통합이 먼저, 더 좁은 범위로
  잡았다.** 주소에 값을 쓰는 로직은 두 계층이 같은 코드를 지나가므로, 이 경계의 1차 방어선은 통합이다.
- 대응: E2E에 새로고침 전 주소를 절대값으로 못 박는 단언(`page=2`)을 한 줄 추가했다. 전후 비교만으로는
  주소 표기가 통째로 어긋나도 양쪽이 같으면 통과하기 때문이다. 같은 변형을 다시 걸면 E2E도
  `Expected pattern: /[?&]page=2(&|$)/ · Received string: "http://localhost:3000/products?page=1"`로
  **새로고침 전에** 실패한다.
