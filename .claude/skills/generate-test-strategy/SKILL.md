description: React 컴포넌트·페이지를 분석해 "무엇을 테스트해야 하는가"를 사용자 행위 관점에서 도출하고 우선순위를 제안한다. 테스트 코드는 작성하지 않는다. "테스트 전략 뽑아줘", "뭘 테스트해야 하는지 분석해줘", "테스트 시나리오 후보 뽑아줘" 요청 시 사용.
---

## 역할

이 스킬은 화면(컴포넌트/페이지) 하나를 받아 테스트 전략(우선순위·시나리오·쿼리 선택)만 제시하는 분석 파트너다. **테스트 코드를 직접 작성하지 않는다** — 단언(expect)의 내용과 모킹 경계는 사용자가 직접 정해야 하는 결정이기 때문이다.

---

## Step 1 — 분석 대상 입력

AskUserQuestion으로 분석할 파일을 입력받는다.

```
질문: "전략을 뽑을 화면/컴포넌트 경로를 알려주세요."
      (예: src/_pages/product-list/ui/ProductListSection.tsx)
```

- 전체 경로가 주어지면 바로 Read.
- 파일명만 주어지면 `find src -name "<입력값>.tsx" -o -name "<입력값>.ts"` 로 탐색 후 Read.
- 페이지 단위라면 하위에서 참조하는 주요 컴포넌트·훅도 함께 Read해 시나리오 파악에 반영한다.

---

## Step 2 — 5단계 분석 실행

파일을 Read한 뒤 아래 순서대로 분석한다. 각 단계 결과는 다음 단계의 입력이 된다.

1. **사용자 시나리오 나열** — 이 화면에서 사용자가 할 수 있는 행위를 나열한다. ("상품 목록을 본다", "카테고리를 바꾼다" 등)
2. **핵심 행위 도출** — 각 시나리오에서 검증해야 할 "사용자가 보는 결과"를 뽑는다. 내부 상태·함수 호출이 아니라 화면에 드러나는 결과여야 한다.
3. **케이스 분류** — 각 핵심 행위를 성공 / 실패 / 로딩 / 에러 / 엣지 케이스로 나눈다.
4. **우선순위 정렬** — "이 기능이 깨지면 사용자가 가장 화날까?"를 기준으로 비즈니스 임팩트 순으로 정렬한다. 커버리지 숫자가 아니라 실패 비용으로 판단한다.
5. **RTL 쿼리 제안** — 각 항목을 어떤 쿼리로 찾을지 제안한다. `getByRole` → `getByLabelText` → `getByText` 순으로 우선 검토하고, `getByTestId`가 필요하면 왜 상위 쿼리로 안 되는지 이유를 함께 적는다.

---

## 출력 형식

```
## 테스트 전략 — <파일명>

| # | 시나리오 | 핵심 행위(사용자가 보는 것) | 분류 | 우선순위 | RTL 쿼리 제안 |
|---|---|---|---|---|---|
| 1 | ... | ... | 성공/실패/로딩/에러/엣지 | 상/중/하 | getByRole(...) |

### 우선순위 근거
- <상위 항목이 왜 먼저인지 한 줄 근거>

### getByTestId 제안 항목 (있는 경우)
- <항목> — 이유: <role/label/text로 안 되는 구체적 이유>
```

---

## 제외 사항 (반드시 지킨다)

- 테스트 코드를 직접 작성하지 않는다.
- 구현 세부사항(내부 state, 내부 함수 호출 여부, CSS 클래스)을 테스트 대상으로 제안하지 않는다.
- 스타일·색상·레이아웃 테스트를 제안하지 않는다.
- 단언 문구·모킹 경계의 최종 결정은 사용자 몫이다 — "이렇게 정하세요"가 아니라 "이런 후보가 있습니다" 형태로 제시한다.

## 공통 주의사항

- "빨간불이 되면 무엇을 알게 되는가"가 "코드가 잘 돌아간다"류로 빈약하면 2단계(핵심 행위 도출)로 되짚어 다시 정의한다.
- 분석 후 "다른 화면도 분석할까요?" 를 묻는다.
